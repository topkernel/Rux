晶核架构(Seed-Core)

最小可信核心 + 其余全部子系统为编译期保证安全的服务 crate · 唯一判据、依赖方向、留核四规则、调用三形式、接口设计规则、不可还原底线、三层防线、业界对比、S1 案例、实测尺寸与落地状态 · 设计正本:docs/architecture/seed-core-design.md · 接口规则:docs/architecture/crate-plan.md §3a · 落地状态截至 2026-11-23

命名(2026-11-22):Seed-Core / 晶核,取材料学隐喻:约 3,000 行手写核心是晶种(seed crystal),全部服务代码在类型格架(forbid 属性 + 借用检查)上结晶为安全代码;编译器是结晶条件。晶种极小,却决定整块晶体的完整性。该名字刻意区别于微内核(地址空间隔离、每次跨服务通信约 1,000 个 CPU 周期的 IPC 边界)—— 晶核架构完全没有地址空间边界(§8)。本页是该设计文档的完整展开;文档地位为设计正本(2026-11-22,用户指令:"把 TCB 缩到最小;理想情况下每个子系统都成为一个 crate 并且是安全的"),取代 crate-plan.md 的终态一节,但其迁移机制(五步迁移流程)仍然有效;执行按阶段顺序进行,不提前落地任何一步。

§1唯一判据与尺寸指令

内核的终态是一个小的可信 crate 加上由 forbid 属性约束的服务 crate 集合。对每一行代码的判据只有一个问题:

这行代码能否活在 #![forbid(unsafe_code)] 之下?
  • 能 → 它属于某个服务 crate(编译器保证安全)。
  • 不能 → 它属于 rux-core,携带一条 INV 契约或 F 行登记,并被验证栈(Kani/Miri/Verus)覆盖。

unsafe 没有第三种归宿。把"框架"当作剩余代码杂物收容所的用法被废除:留在核心里的代码是因为它不可能写成安全代码,不是因为它还没被改写。

术语说明(首次出现即定义)。信任计算基础(TCB,trusted computing base):内核安全性质所依赖的全部代码集合 —— TCB 里任何一处的错误都可能破坏这些性质;TCB 越小,需要逐行人审的面积越小。forbid(crate 级禁止属性):在 crate 顶部声明 #![forbid(unsafe_code)] 后,该编译单元内的任何 unsafe 代码都是编译错误(对抗性验证:向服务 crate 注入 unsafe 必使其自身构建失败),且该属性不能被 crate 内的模块降级为警告或关闭。INV 契约(INV contract):每一段留在核心的 unsafe 代码都附带一条编号的机器可验证前提声明。例如 INV-SCE-3 声明:"全局运行队列的存储由 grq_init 在 GRQ_READY 标志的 CAS 竞争下写入一次;后续读取仅发生在该标志的 Acquire 屏障之后"—— 这规定了该 unsafe 块成立所需的内存可见性条件。每条声明回答三个问题:该代码依赖什么前提才能正确执行(如"此页已映射且对齐")、执行过程中不得违反什么约束(如"不得在持有此指针时调用可能释放它的函数")、退出时必须完成什么清理(如"必须释放引用计数")。声明登记在 docs/architecture/safety-and-performance.md 中,与代码行一一对应。F 行登记(F-row):对经论证无法用安全代码重写的 unsafe(如上下文切换必须直接操作 CPU 寄存器,无法通过 Rust 安全子集表达),在不可缩减性登记表中记录一行,内容包括:所属函数、行数、无法重写的原因、参考实现中的对应代码(如 Linux 的 entry.S)。两类记录合计:约 3,000 行核心代码中每一行 unsafe 都有对应的审计条目,覆盖率 97% 以上。

尺寸指令(2026-11-23)

上面的判据决定了 unsafe 代码住在哪里;它没有决定多少安全代码留在核心 —— 而到 2026-11-23,答案是"绝大部分都在":kernel/src 共 286,139 行,含 1,838 个 unsafe 块和 238 个 unsafe fn/impl 体。战役余下部分的指令是:

核心的代码在性能不受影响的前提下尽可能小。离开核心的代码按子系统组织。

后面的章节回答三个由此而来的问题:核心为什么不能依赖服务 crate(§2);哪些代码必须留下(§3);一次调用跨过 crate 边界要付什么代价(§4)。

§2依赖方向:核心为什么不能依赖任何服务 crate

"服务依赖核心、永不反向"这条规则通常用构建图来论证。真正的原因是它决定了"核心是正确的"这个论证能否闭合。

核心维护内核的数据结构不变量:任务槽生命周期、运行队列的锁协议、页表原子更新、引用计数。要论证一个不变量成立,必须知道一切能改变它所约束状态的代码:改了什么、以什么顺序、在哪把锁下。

如果核心直接调用某个服务 crate,这个论证无法闭合。要证明 __schedule() 保持运行队列协议,就必须跟进调用进入调度策略 crate —— 而那个 crate 随每一次唤醒或负载均衡修改而变化,每次修改都可能撤走核心证明所依赖的前提。核心的可信计算基于是"它自己 + 它能调用到的一切",一个随服务增长而无固定边界的集合。

依赖方向反过来之后,核心触达服务的唯一途径是回调函数表(callback table:核心定义每个槽位的函数签名,服务在启动时把实现登记进表)。一行签名如 pick_next_task: fn(&CpuRunQueue) -> TaskRef,本身就界定了被调方"能做什么":读运行队列、返回一个任务引用。它拿不到锁的内部状态,改不了队列结构,碰不到正在切换的上下文 —— 不是因为它的代码被评审过,而是核心发布的类型根本表达不出这些操作。核心的论证由此闭合:无论回调内部做什么,它只能经核心发布的接口行动,核心的不变量独立于服务 crate 的内容而成立。

核心依赖某个服务 crate核心不依赖任何 crate
核心的可信计算基核心 + 它能调用到的每一行仅核心自身
修改一个服务 crate 之后核心不变量必须重新论证核心论证不受影响
不变量靠什么保证服务代码"恰好没做坏事"接口类型表达不出"坏事"

所以回调函数表不只是带性能代价的间接调用层(§4、§11 的 S1 案例);它是服务对核心全部视野的机器检查声明。这也回答了热路径字段为什么留在核心(§3 规则 3):一个由核心锁协议保护更新的字段,绝不能经任何回调可获得的类型触达 —— 否则回调就能在该协议之外改它。

§3留核四规则

四类代码必须留在核心;其余都可以离开。

  1. 某个热路径调用点按名调用的函数。热路径调用点是:陷阱进入与返回、上下文切换、缺页路径、VFS 路径走查、bio 与页缓存、分配器入口、锁原语、时钟节拍、IRQ 派发。函数搬走后,这个调用就得走回调函数表 —— 一次编译器无法内联的间接调用(函数指针的目标是运行期值)。函数留在热调用方直接可达的地方。
  2. 某个已有服务 crate 按名调用的函数。服务 crate 只触达核心,不触达另一个服务 crate(横向边是 Cargo 必须排序的子系统间依赖,而环会被拒绝)。因此 rux-syscall 要用的函数必须在核心里。实例:restore_sigcontext,被 sys_rt_sigreturn 调用 —— 信号工作线 2026-11-23 发现的案例。
  3. 某个热路径直接读写的字段。这是对字段的约束,不是对类型的约束。服务 crate 可以自由使用核心定义的类型(服务 → 核心是允许方向);必须留下的是热路径触碰的字段集合,因为 Cargo 禁止核心 → 服务。以 Task(共 105 个字段)实测:
热路径触碰字段数字段
上下文切换7thread, kernel_stack_bottom, address_space, state, pid, on_cpu, pick_state
陷阱路径10pt_regs, address_space, kernel_stack_bottom, preempt_count, sigmask, pid, tgid, utime_ticks, stime_ticks, comm
调度器6ti_cpu, ti_flags, state, sched_entity, rt_entity, pid
VFS 路径走查7cred, fs_arc, pgid, rlimit, try_fdtable, ns_pid, umask

合计约 20 个。其余约 85 个(ptrace 状态、robust list、syscall/exit/reap 记账、统计)热路径从不读取。这样的类型可以拆分:核心块持有热字段 —— 偏移与缓存行邻居都与今天相同 —— 服务块经一个热路径从不跟随的指针触达。热路径为此支付零成本:它访问的每个字段仍在核心块的原偏移上。该拆分是横跨全部子系统的结构性工作,排在函数级搬迁之后;在那之前,含任一热字段的类型保持整块,它的冷方法以自由函数的形式先离开。

  1. unsafe 且位于 F 行地板上的函数 —— pt_regs 写入、在用户栈上构建信号帧、切换本身。按名扫描看不见这类函数;拥有它的工作线把它留下并记录原因。

其余一切离开核心。一个既不被热路径按名调用、也不被服务 crate 按名调用的函数,只从冷调用点到达;冷调用点经表向上调用是可接受的。搬走的代码自己调核心的方向是直接跨 crate 调用,可内联。§4 给出两个方向的完整不对称表。

§4调用跨边界的三种形式

"搬代码是否损失性能"的每个问题都归结为调用如何跨过 crate 边界。本内核存在三种形式;整个战役的放置规则由此推出。

直接调用按名指认被调方。mm_edges::zero_range(...) —— 编译器看见目标、检查签名、发射一个固定地址的 call。跨 crate 没有任何变化:被调方的中间表示(MIR)随 rlib 元数据传递,优化器可以跨边界内联,与同一 crate 内完全一样;LTO 使之必然。因此只要依赖方向正确,直接调用是免费的 —— 服务 crate 调核心,无论调用点多热,都不付费。

间接调用在运行期读取目标。从回调函数表加载的函数指针:

// 核心侧的派发点
let next = (hooks.pick_next_task)(&rq);

编译器无法知道槽位里是哪个函数 —— 它是启动时才发布的值 —— 所以不能内联、不能对实参做常量折叠,且必须让该调用按破坏全部调用方保存寄存器集处理。单次间接调用本身只要几纳秒;真实代价是它所禁用的优化乘以调用频度:在被调方已知的前提下编译器能做的一切(实参特化、跨函数对的死代码消除)在每个调用点全部失效。S1 实测(S1 = 调度子系统的机制/策略分离,§10)是记录:每次上下文切换约 40 个观测行各一次间接调用,切换中位数 +25.1%(1.718 → 2.149 µs);把静态量收回框架侧改为直调后回到 +1.7%(§11 全程记录)。

接口方法(vtable 字段)是调用方本来就在付的间接调用。FileOps 上的 ops.fault(file, off) 读一个字段并调用它。这不是新增成本 —— 该调用在搬迁前后同样是虚调用 —— 把一个叶子实现挪进已有的 FileOps 槽位不增加任何东西。ext4 迁移把读写路径放在 FileOps.fault / FileOps.write_at 上而不是新增表行,就是这个原因。

放置规则由三种形式直接推出:

调用点被调方迁往成本规则
热路径(陷阱、切换、缺页、走查、分配、节拍)某个表行后面每调用点一次间接调用,不可内联被调方留在核心
热路径已有 vtable 字段后面零新增成本允许;数据路径首选
冷路径(挂载、sysctl、procfs 展示、exit 钩子)某个表行后面在本就做 µs–ms 工作的路径上加几 ns允许
任意服务 crate 调用点核心内直接调用,可内联永远允许

两个方向的不对称,汇总一张表:

方向机制成本
服务 → 核心直接调用,跨 crate 内联(rlib 元数据携带 MIR;LTO 补全)零
核心 → 服务,冷调用点经表一次间接调用冷路径上可忽略
核心 → 服务,热调用点每调用点一次间接调用,不可内联S1 回归:上下文切换 +25.1%

决定布局的是间接调用的两个性质,而非品味:(1)内联要求被调方是编译期常量,表槽位永远不是;(2)代价随调用频度相乘 —— 冷路径上可忽略、热路径上可测量。同一行表在一个子系统里免费,在另一个里就是 25% 的回归。

§5接口设计规则:什么让闭合论证为真

§2 的闭合论证成立的前提,是发布的接口真的表达了约束。一个类型为 fn(*mut Task) 的回调把整个任务经裸指针交给被调方,什么都不保证 —— 表就成了形式主义。让边界为真的规则:

  • 类型携带前提。核心发布类型化句柄(TaskRef、TaskBorrow、Arc<T>),不发裸指针。服务需要文件私有数据时,调用 fs::unsafe_edges::file_privdata_take_arc::<T>(file) -> Option<Arc<T>>;返回值上借用检查器继续工作。它写不出 unsafe { &*p } —— crate 禁止 —— 而且它也没有 p 可写。
  • 可见性即边界。同一 crate 内 pub(crate) 处处可达;跨 crate,服务只看得见核心标记为 pub 的条目,而每个 pub 条目是一次有名字、有签名、有 INV 契约的正式发布。文件系统代码迁入 forbid crate 时(2026-11-23),散落各处的裸指针访问必须收敛到 unsafe_edges.rs 里少数几个类型化函数上:访问没有消失,而是变成了一份可以逐条审计的简短清单。
  • 热路径绝不经表调用服务 crate(crate-plan §3a 规则 2):数据路径上的接口要么取已有 vtable 字段(FileOps.fault、FileOps.write_at —— 调用方本就执行的字段分发),要么取框架侧静态量上的直接 #[inline] 包装,绝不新增函数指针表行。表行只用于冷路径;当表行体是观测仪器时,调用点可以按仪器是否武装跳过它。
  • 表是服务的全部视野。服务只经发布函数与被给予的表行触达核心。服务需要表没有提供的东西时,答案是加一个类型化核心函数或一个表行 —— 不是放宽某类型的可见性,也绝不让一个表行的实现去调用派发同一表行的包装函数(那次自递归曾让调度迁移停滞)。
  • per-CPU 区建立之前运行的代码不得取锁。这里的每个 Spinlock::lock() 都读 per-CPU 状态(抢占计数、持有者 CPU 号),在 x86_64 上经 %gs 相对寻址,而 rust_main 期间 GS 基址还是 0。在那个时点发布注册信息要用 OnceSlot 或普通原子变量。服务测试登记表的第一版在那里取了 Spinlock,x86_64 单元测试内核在第一次打印之前就异常了(2026-11-23)。

跨 crate 接口设计三规则(crate-plan §3a,2026-11-23 采纳)

设计任何回调表或 trait 接口的三条规则 —— 与参考单体内核中 Rust 叶子模块用以压低 FFI 相邻抽象成本的同一组原则。Rux 用实测回归换来了它们,它们对之后每次迁移有约束力:

  1. 按关注点分表,绝不做巨表。每个生命周期/消费者一张表(fs 侧是 MountFn / notify / ops / relocation / FsHooks 五张表;mm 侧是 MmHooks 与 MmPolicyHooks 两张)。行数超过约 20 的表必须拆分,或在接口文档注释里说明其宽度为什么合理。
  2. 热路径静态分发优先。数据路径上的接口取已有 vtable 字段(如 FileOps.fault / FileOps.write_at)或静态量上的直接 #[inline] 包装,不新增函数指针行。凭据:S1 每次切换约 40 次间接调用曾使 p2_ctxsw +25.1%,去虚化后 +1.7%;R5 的读写路径走 FileOps 槽位,零新增间接。函数指针表行只用于冷路径(挂载行、procfs 展示、sysctl、exit/exec 钩子),体为诊断时可加武装门控。
  3. 薄而机械的适配层。接口签名携带本生错误类型(Result<_, i32> errno 或领域枚举),适配层零逻辑 —— 函数体逐字搬移;转换是一行的机械动作。若接口体需要逻辑,那逻辑属于边界某一侧,不属于接口。

§8为什么不用地址空间隔离:与微内核对比

购买故障隔离的经典办法是给每个服务独立地址空间(seL4/L4 族):坏驱动破坏不了内核内存,因为它寻址不到。代价是边界本身 —— 每次跨服务操作都是一次经上下文切换的 IPC,最优快速路径约 1,000 个周期,并沿"缺页 → 驱动 → 文件服务"调用链逐级相乘(Mach 内核的历史教训;L4 的快速路径收回了很多,但重系统调用路径上没有全部收回)。

晶核架构静态地买到同一内存安全性质,运行期成本为零:一个 #![forbid(unsafe_code)] crate 表达不出野指针、释放后使用或数据竞争 —— Rust 类型系统提供了 C 微内核里由地址空间提供的东西,而没有运行期边界。跨 crate 调用是普通函数调用(LTO 内联;M3 迁移在派发表在场时验证了零行为变化)。这是 RedLeaf/Framekernel 一脉:语言隔离、不用地址空间,同时保留硬件后备(§7)而非把全部赌注押在类型系统上。

两种设计共同如下的地方:逻辑缺陷(死锁、错误决策、泄漏)照样通过;只有内存安全类不同。微内核为第 1 层(类型层等价物)每边界付约 1,000 周期;本设计以 0 + 约 50 + 0 同时买到三层。

§9业界四种 Rust 内核路线,与晶核的综合位置

业界 Rust 内核对"unsafe 放在哪、TCB 怎么划"有四类回答。晶核(§1 所定义)不是某一路线的极端化 —— 它组合其中几家的具体优势,并加固它们都没有机器检查的一环。

  • 微内核路线:Redox、Tock、Hubris。Redox 是 MINIX 式微内核(约 16,000 行内核;驱动与服务在用户态,MMU 隔离)。Tock 面向嵌入式:极小可信内核 + 以 Safe Rust 编写的"胶囊"驱动,用户进程由 MPU 保护 —— 代价是每加一个胶囊都扩大 TCB(实测 TCB 占比约 43.8%)。Hubris(Oxide)在构建时静态分配全部任务;内核、驱动与任务处于硬件内存保护隔离的独立域。共同立场:靠硬件隔离(MMU/MPU)、内核极小、每次跨组件调用付 IPC。
  • Framekernel 路线:Asterinas(最近的亲戚)。framekernel(术语来自 Asterinas,USENIX ATC'25)把内核逻辑上分为 Framework(唯一允许 unsafe 的层)与 Services(全部 Safe Rust),同一地址空间、同一特权级 —— 服务调用是普通函数调用,无 IPC 开销。实测:TCB 占比约 14.0%(对比 Tock 43.8%、Theseus 62.4%、RedLeaf 66.1%);LMBench 几何均值 1.08× 参考单体内核,Nginx 1.17,Redis 1.31。这与本设计的机制/策略分离在结构上是同一机制 —— 差别在于 Asterinas 的 Framework 是单一 crate 内靠约定与评审维持的逻辑层,而晶核把边界画在 crate 编译单元上并让工具链检查它。这是强制力硬度的差别,不是风格差别。
  • 叶子式路线:参考单体内核中的 Rust 叶子工作。不重写内核:调度器、mm、VFS、RCU 仍是 C;Rust 活在叶子(驱动、文件系统模块、binder 类子系统)。unsafe 边界是内核 crate 导出的安全包装集;下面是进入 C 的 FFI。TCB 是整个 C 内核 —— Rust 侧保证只覆盖新写的叶子。它对本设计的参考价值不是架构而是抽象手法:刻意最小的 trait(FileSystem、Operations、INodeOperations 保持分离,而非一个 50 方法的巨型 trait)、静态分发优先于 trait 对象、薄而机械的错误映射。本设计正是用这些手法压低跨 crate 接口的间接调用开销。
  • 单地址空间 cell 路线:Theseus。一个地址空间、一个特权级;主张"语言内设计"(intralingual)—— 把尽可能多的操作系统记账交给 Rust 编译器本身 —— 组件是可动态加载的 crate("cell"),以避免状态外溢(组件交互引起的持久状态变化,它使故障隔离与在线更新困难)。TCB 占比约 62.4%,高于 Asterinas,因为更多组件保持受信。Theseus 明确以"单地址空间、单特权级匹配 Rust 编译器执行模型"论证其模型 —— 这是对本设计"机制留核心"决策的独立佐证。

晶核从各家取什么,加什么。取微内核的最小信任核纪律 —— 底线逐行登记并各带参考对应物与 F 行编号,不是一个"区域";取 Framekernel 的单一地址空间与零 IPC 边界 —— 跨 crate 直接函数调用,LTO 内联,比 RPC 薄整整一个协议层,接口的间接调用成本一旦冒头就去工程掉(上下文切换 +25.1% 经去虚化收回 +1.7%),而不是接受它;取 Theseus 的 crate 即隔离单元、以及"单地址空间是编译器自身理解的执行模型"这一论断;取叶子式的最小 trait、静态分发、薄错误映射手法,让回调表保持便宜。而业界没有一个 Rust 内核把边界放进构建系统 —— 包括 Asterinas 在内:晶核的每服务 crate #![forbid(unsafe_code)] 让在服务代码写 unsafe 成为编译错误而非评审发现(对抗性验证);Cargo 依赖图拒绝环,分层违规是构建失败;CI 对属性集合做单调性检查,属性移除即失败;类型层之后还有 MPK 硬件后备(WRPKRU 实测 47–49 周期,故障注入实证)。逻辑层会因约定松弛而腐蚀;编译错误根本写不出来。这就是晶核的主张:单体内核级性能、比上表所有实测占比更小的 TCB、以及该空间里唯一由工具链而非流程守护的边界。

§10机制与策略分离(S1/M1):编译器强制的经典原则

S1 是"机制/策略分离"(mechanism/policy separation,经典操作系统设计原则)的第一个编译器级强制实现。机制指执行状态变更的底层操作 —— 上下文切换、全局运行队列的锁协议、当前任务指针的寄存器读取、任务槽位的分配与回收 —— 这些操作直接维护内核的数据结构不变量,保留在核心 crate 中接受逐行审计。策略指基于机制做出的决策 —— 选择下一个运行的任务、决定唤醒任务的放置 CPU、计算节流阈值 —— 这些决策仅通过机制暴露的类型安全接口访问数据,移入独立的服务 crate 并声明 #![forbid(unsafe_code)]。传统上这一分离仅靠代码评审维护;此处由编译器静态保证:策略代码中的任何 unsafe 使用都是编译错误。回调函数表与私有接口 API 构成机制向策略发布的完整调用契约。M1 对内存管理子系统采用相同的分离。

命名(2026-11-22 用户指令):服务 crate 不带 -policy 后缀 —— 分别是 rux-sched(S1)与 rux-mm(M1)。S1 = 调度子系统的机制/策略分离,M1 = 内存管理子系统的同等分离。

§11S1 案例全程:接口开销回归与修复,两项保证同时成立

S1 落地时带了一个性能回归,性能门禁拒绝放行;它的解决是"本设计同时保证安全与性能、互不为代价"的长期证据。全程记录,带数字(p2_ctxsw 是 pbench 微基准的上下文切换行):

  1. 回归。迁移完成后,pbench p2_ctxsw 读数 2.149 µs,同窗口 main 为 1.718 µs(+25.1%)—— 超出调度看护域的 ±20% 带。合并被扣住直至修复(门禁政策:功能正确但性能回归的改动不予合并)。
  2. 根因 —— 不是"跨 crate 调用慢"。直接的跨 crate 调用内联没有问题(rlib 元数据携带 MIR;LTO 补全)。成本出在分发机制:向上调用(核心 → 策略)走登记的函数指针表,而经函数指针的调用是间接的 —— 被调方是运行期从表里加载的值,编译器不可见,LTO 或任何东西都无法内联。第一版 SchedHooks 表有 111 行,观测占大头:每次上下文切换约 40 行被触发(sched_cs_stamp ×4/schedule、pick_trace ×2–3/切换、pick_gen 发布/退役、ww_record、唤醒普查、vr_canary、类计数器),每行支付 垫片 → 包装 → 槽位加载 → 间接调用。按调试类每次约 10 ns 计约 400 ns —— 与实测差值(431 ns)在噪声内一致。
  3. 修复 —— 让热调用重新变成直接调用。三个动作,零行为变化:(a)33 个观测行离开表 —— 它们的静态量移到框架侧(entities.rs),框架以直接静态调用调用它们,可内联;计数器记录不变。(b)真正动态的分发收敛为一个粗粒度入口:pick_next_task —— 整个拣选循环在单次跨界内于策略侧运行,而不是每步一次跨界。(c)三个条件诊断行改为武装门控包装(包装检查与函数体相同的框架侧标志;未武装的启动完全不触碰接口)。武装模式输出验证逐字节一致(恰好 40 行 WWTICK 预算)。
  4. 结果。p2_ctxsw 1.758 vs 同窗口 main 1.728 = +1.7%,带内;P4 风暴行 +2.6%;10 次测量启动 + 1 次武装启动零 panic;rux-sched 的 forbid 未被触碰 —— 修复付出零 unsafe:它搬动的是普通安全状态、重塑的是调用点。SchedHooks 表从 111 行减至 78 行。
  5. 提取出的规则(crate-plan §3a,对之后每个接口有约束力):函数指针表行只用于冷路径;热路径取 (a) 整个循环置于一个粗粒度入口之后,边界只跨一次,(b) 已有 vtable 字段(FileOps.fault/write_at —— 字段分发,R5 的读写路径零新增间接),或 (c) 框架侧静态量上的直接静态调用。观测静态量默认放框架侧。
教训,只说一次,用直白的话:crate 边界的安全性是免费的;分发机制才是要花钱的。设计接口、测量它;回归了就修接口 —— 永远不动安全属性。

这个设计保证什么,不保证什么

诚实的边界,免得把主张读过头。两个词先定义:审计记录指把每个 unsafe 区域映射到其 INV 契约或 F 行的记录;发布面指核心为服务 crate 标记 pub 的函数与类型集合。

  • 依赖方向没有让 unsafe 变得不可能;它让服务 crate 的零 unsafe 成为真的。单独的 #![forbid(unsafe_code)] 可以被绕过 —— 一个不能写 unsafe 的 crate 可以调用一个能写的。因为核心不依赖任何服务,服务触达不到任何会写 unsafe 的代码,除了核心的发布函数。
  • 服务代码仍可以调用那些发布函数,其中一些内部是 unsafe。保证的是:每次这样的调用都经过一个有名字、有类型、带 INV 契约的函数,且这些函数是唯一的通道 —— 不是"服务代码做不了坏事"。
  • 函数带契约不等于契约正确。2026-11-23 对该记录的审计发现,1,591 条既有注解中 349 条与它们描述的代码相矛盾。审计冻结(§14 执行顺序的最后一步)是发布面被逐函数检查的地方:每条签名是陈述了前提,还是仅仅文档化了前提。
  • 留下的核心仍是一个可信计算基础。它现在有界、有名、不能悄悄增长;它不豁免于 INV/F 行纪律与验证栈。

§14执行顺序、搁置纪律与未决项

执行顺序有约束力;每个阶段 = 先测量 → 设计接口 → 迁移 → forbid → 测试集:

  1. R1 收口(进行中):syscall 状态 B —— 删除库内文件、全量测试集、对抗性验证。门:三架构、make test、fio 三例、冒烟;计数列开始分裂。
  2. S1 测量(下一步):调度策略/核心边计数(一天,无代码)。然后接口设计 → 策略 crate 迁移 → forbid → 测试集(含 P4 风暴 + ctxsw pbench —— 看护域)。已按此完成(§13)。
  3. M1 测量:mm 策略/核心边。然后同 S1(测试集含 defect-C 对 + mmap LTP 行)。已按此完成(§13)。
  4. R2 网络:实测的 35 处反向调用点搬迁 + 迁移。
  5. R3 fs-svc + R5 ext4:最大的一块;按 crate-plan 逐项测量。
  6. R4 drivers:最后一个服务阶段。
  7. debug 评审:逐仪器裁定 —— 追查已关闭 → 仪器退役(删除);追查仍在 → 仪器移入 rux-debug-svc 置于其开关之后。第一阶段已落地(r83hunt 与 treehunt 连同调用点与门事件删除;−915 debug/ 行);保留家族携带书面退出判据。
  8. 核心审计冻结:最后一轮 INV/F 行登记 —— 核心每一行都在某一行之下;逐块不可缩减性证明( D 轮交付物)此后恰好覆盖 rux-core。这是发现 §12 中 349/1,591 矛盾注解的地方。

每级门禁:常规集合(三架构构建、make test、unsafe_gate、print 逐步收紧、冒烟)+ 该阶段的领域测试集 + crate 范围的 forbid 对抗性验证。一个阶段两次未过其测试集即暂停整条顺序(不在不稳定的基础上堆改动)。搁置即成功,不是失败:实测不可分解的反向面使该子系统留在核心侧,数据记录在设计文档中。

边界文件的去向

各子系统的 edges.rs/unsafe_edges.rs 按阶段消解:其中每个函数要么是对核心原语的调用 —— 边函数退化为薄再导出而后消亡;要么是真正本地的 unsafe —— 它带着自己的 INV 行迁入 rux-core。终态没有各子系统的边界文件;只有核心的登记表。

风险与未决项(如实)

  • 核心仍是约 3,000 行手写 unsafe。设计把它压到参考内核自己的地板类;没有消灭它。验证栈是补偿控制。
  • 策略/核心接口可能出错(defect-C 教训:锁域之间的接口是竞态所在)。每个分离的接口过故障测试集,不只过常规套件。
  • 热路径成本:策略入 crate 意味着调度与缺页路径上的跨 crate 调用。缓解:工作区范围的 LTO + 内联本就是构建形态;每次分离由 ctxsw/缺页 pbench 行把门(§11 是实例)。
  • 搁置即成功:实测不可分解的面使该子系统留核,数字记录在案(vma + mm_struct、binder.rs、sysv_sem,§13)。
