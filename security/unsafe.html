unsafe 审计记录

内存安全 TCB 的定义、收拢规则、机器 census 数字与后续路线 —— 回答"unsafe 到底有多少、在哪、受什么约束" · 正本:docs/architecture/safety-and-performance.md(收拢战役 + INV index)、docs/architecture/kernel-layers.md(分层规则)

§1内存安全 TCB 的定义

本内核的内存安全 TCB(可信计算基)定义为:内存安全性依赖人工评审而非 Rust 编译器的代码 —— 即 unsafe 区域内的全部行。其余代码内存安全由构造保证(编译器强制)。2026-11-27 收拢战役落地,2026-11-28 完成逐语句收窄 + safe 函数回迁:这些行全部集中在 18 个按子系统的审计 unsafe.rs 文件与 tests/ 中,其余 ~401 个文件在编译器层面禁止 unsafe(机器门禁全库 rc=0)。双口径读数:unsafe 共 3,936 行 = 397,552 行(kernel/src 物理行,不含 tests/)的 0.99% —— 块口径 1,329 个块 / 3,661 行(0.92%),unsafe fn/unsafe impl 口径 165 项 / 275 行(0.07%);战役弧线:22,881 行 = 5.76%(2026-11-27 收拢后)→ 3,936 行 = 0.99%(2026-11-28),收拢前登记表为 6,396 处 unsafe 区域。

诚实边界(每份审计记录报告携带):Rust 的 unsafe 纪律只覆盖意外内存不安全。它不是对逻辑缺陷、ABI/规范违反或构建链污染的证明 —— 后者由形式验证、缺陷分类学与压力测试承担(见本栏其他页)。

§2收拢规则:审计集合与禁止集合

集合内容unsafe 政策
审计集合(18 文件 + tests/)每个子系统一个 unsafe.rs 审计文件(arch/mm/fs/sched/process/drivers/ipc/net/sync/syscall/dfx/trace/timer/interrupt/perf/io_uring/safety/security);硬件/特权操作(trap 入口、页表、上下文切换、裸 MMIO/DMA、uaccess、底层同步原语)都住在对应子系统的审计文件里允许 unsafe;每块携带 INV 契约(编号的机器可验证前提声明),文件头注释携带契约清单;逐语句粒度 —— 语句只在编译器要求时才留在 unsafe 内(E0133),每个区域都是编译器验证的必要性,块边界无代码生成效应
禁止集合(401 文件)全库其余全部 kernel/src 文件文件级 #![forbid(unsafe_code)] —— 编译器强制零 unsafe;机器门禁 scripts/gate_unsafe_mainline.py 全库 rc=0,审计文件之外出现任何 unsafe 即构建失败
tests测试代码可含 unsafe,不入头条口径(审计面针对 kernel/src)
  • 新 unsafe 无处可放:禁止集合里写 unsafe 是编译错误,不是评审意见;要加 unsafe 必须进对应子系统的审计文件并写 INV 契约 —— TCB 增长被编译器与门禁约束,而非约定约束。
  • 用户内存边界:系统调用入口统一校验并翻译用户指针;内核其余部分不直接触用户内存 —— 用户拷贝走 arch/uaccess_safe.rs 的地址/切片类型化 copy_in/copy_out(INV-UACCESS-1:内核侧操作数由类型系统证明,用户侧 access_ok 检查 + 异常表兜底)。

§3审计记录数字(机器 census + 双口径)

区域口径(逐语句粒度)

每个 unsafe 区域都是逐语句粒度:语句留在 unsafe 内当且仅当编译器要求(E0133 指引的收窄,2026-11-28 落地;零行为变化 —— 块边界无代码生成效应)。arch 层地板:arch/unsafe.rs 承载 2,181 行 unsafe(文件共 25,343 行);73 个 safe 函数已从该文件回迁到各自归属的子系统文件。

口径说明:双口径(块体行 + fn/impl 体行)是头条数字,语句是审计登记的单位,两者都由脚本机器生成。外部参照:Asterinas(USENIX ATC'25,同类 Rust 内核)报告内存安全 TCB ~14%(未按双口径公布)。

§4forbid 覆盖与后续路线

  • 当前:401 个文件带 #![forbid(unsafe_code)],机器门禁 scripts/gate_unsafe_mainline.py 全库 rc=0 —— 收拢战役的目标态(审计文件之外零 unsafe)已达成并由机器强制。
  • 收拢战役的量化目标(≤5,000 行、≤1%)已达成:3,936 行 = 0.99%;审计地板留在机器门禁与编译器双重约束之下。
  • 分级审计继续:class 1(带检查的访问器读)→ class 3(裸指针 + 手写不变量);每个审计块的 INV 契约登记于 safety-and-performance.md 的 Primitive INV index。

§5分层论证:为什么这个形状值得信任

  • 类消除论证(对照 C 内核 CVE 史):越界写(bounds-checked slice)、Arc 属主的 use-after-free/double-free、类型化共享态数据竞争(Send/Sync)、迭代器失效(borrowck)、格式串注入(typed formatting)—— 这些主导类别在 safe 代码中不可表达;缺陷分类学的 0 例指针表达式缺陷是同一条论证的实证面(见 分类学)。
  • 密度论证:arch 层地板文件(arch/unsafe.rs,2,181 / 25,343 行)承载三架构硬件操作的必然集中,是收拢设计的活样本 —— unsafe 面积与原语复杂度成正比、与 API 面积无关。
  • 配对论证:每个原语配 (a) Kani harness,(b) proptest,(c) Verus 函数规约(登记的下一步,先做页标志/引用计数代数);RustBelt 作为信任锚引用而非构建依赖。
  • 预算论证:双口径读数的单调下降规则(战役弧线 5.76% → 0.99%)+ 禁止集合里 unsafe 是编译错误 —— TCB 增长被编译器与机器门禁约束,而非约定约束。
