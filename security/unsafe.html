分层 unsafe 台账

内存安全 TCB 的定义、分层规则、逐目录预算与收缩路线 —— 回答"unsafe 到底有多少、在哪、受什么约束" · 正本:docs/architecture/kernel-layers.md、docs/development/tcb-ledger.md(脚本生成)

§1内存安全 TCB 的定义

本内核的内存安全 TCB(可信计算基)定义为:内存安全性依赖人工评审而非 Rust 编译器的代码 —— 即每个 unsafe 块内的全部行。其余代码内存安全由构造保证(编译器强制)。工程目标是以语言级隔离赋予宏内核接近微内核的安全性:将 unsafe TCB 收缩到一个小的特权 Framework 层。

诚实边界(每份台账报告携带):Rust 的 unsafe 纪律只覆盖意外内存不安全。它不是对逻辑缺陷、ABI/规范违反或构建链污染的证明 —— 后者由形式验证、缺陷分类学与压力测试承担(见本栏其他页)。

§2分层规则

层内容unsafe 政策
Framework硬件/特权 TCB:trap 入口、页表、上下文切换、裸 MMIO/DMA、uaccess、底层同步原语(arch/、mm/、interrupt/、virtio·intc·timer·pci 核心、console/printk/sbi/main/init 等)允许 unsafe;每个块须携带 // SAFETY: 不变量注释,覆盖率入台账
service全部面向用户态的层(syscall、fs、ipc、net、process、sched 上层、cgroup、procfs…)#![forbid(unsafe_code)] 为目标态(当前 47 文件编译期禁止 + 63 文件已无 unsafe)
diagnosticsdfx/ 取证仪、裸内存工具单独统计 —— 诊断工具的 churn 不得藏进 Framework 桶
test测试代码不入头条口径
  • 分类器为最长前缀匹配;未匹配路径默认落入 service —— 新文件从最安全的桶开始,晋升须显式操作。
  • 胶囊边界(Tock 模式):系统调用入口统一校验并翻译用户指针;内核其余部分不直接触用户内存。syscall/io.rs 的 69 个 unsafe token 清零是该模式的实例 —— 用户拷贝改走 arch/uaccess_safe.rs 的地址/切片类型化 copy_in/copy_out(Framework 新模块)。

§4forbid 运动与收缩路线

  • 第一轮(2026-10-29):113 文件带 #![forbid(unsafe_code)](46 service);第二轮(2026-10-31):首个具名收缩目标 syscall/io.rs —— 69 token → 0。
  • 目标(登记于 security-design.md):forbid 文件 47 → 90,带 unsafe 的 service 文件 123 → 60(两个季度窗口)。
  • SAFETY 注释覆盖 64% → 95%(class 2-3 块)为目标。
  • 分级审计计划:class 1(带检查的访问器读)→ class 3(裸指针 + 手写不变量);台账头条将增加 "service 层 class-3 token 数" —— 真正预测现场缺陷的量。审计覆盖门:scripts/review_coverage.py --check 在树内出现台账未登记文件时使构建失败。

§5分层论证:为什么这个形状值得信任

  • 类消除论证(对照 C 内核 CVE 史):越界写(bounds-checked slice)、Arc 属主的 use-after-free/double-free、类型化共享态数据竞争(Send/Sync)、迭代器失效(borrowck)、格式串注入(typed formatting)—— 这些主导类别在 safe 代码中不可表达;缺陷分类学的 0 例指针表达式缺陷是同一条论证的实证面(见 分类学)。
  • 密度论证:sync 目录 2.8% 的 unsafe 密度是分层设计的活样本 —— unsafe 面积与原语复杂度成正比、与 API 面积无关。
  • 配对论证:每个 Framework 原语配 (a) Kani harness,(b) proptest,(c) Framework 收缩后 Verus 函数规约(登记的下一步,先做页标志/引用计数代数);RustBelt 作为信任锚引用而非构建依赖。
  • 预算论证:14.0%(双口径)的单调下降规则 + 每处新增 unsafe 须在 commit body 说明"为什么 safe 不可能"—— TCB 增长被流程约束而非约定约束。
