r21-bugs lane follow-up verdicts (worktree r21-bugs, branch origin/r21-bugs)

Bug 1 (coredump KERNPANIC): REAL, fixed (b835e56e).
  Root cause: do_coredump's dump_read() walked the dying task's page
  tables with a hand-rolled SV39 loop on every arch. On x86_64 it
  misread x86 PTEs into off-machine physical addresses and the content
  memcpy faulted in kernel mode (kill11, deterministic 3/3, fault at
  phys 0x1c0400000 on a 2G machine; r21 saw it under waitpid01/kill11
  load). Fix: route through arch::mm::mm_ops::PageTableWalker like the
  rest of the kernel; e_machine now arch-selected too.
  Verified: kill11 3/3 + waitpid01/abort01 rc=0, zero kernel faults.

Bug 2 (syslog negative length SUCCESS): REAL, fixed (d98f3272).
  Root cause: syslog(2) declares `int len`; a C caller passing -1 via
  varargs leaves the arg register's upper 32 bits zeroed, so args[2]
  read raw was 0xFFFFFFFF (positive). The EINVAL guard never fired and
  read_all copied 8836 ring bytes past the caller's 1-byte buffer.
  Fix: truncate to i32 and sign-extend (len and the type-8 level).
  Verified: syslog12 2/2 rc=0.

Bug 3 (sem_nsems=0 from IPC_STAT): REAL, fixed (56ce13a8).
  Root cause: commit 44b70b26 forced the 88-byte asm-generic semid64_ds
  on every arch, but the x86 uapi pads each time_t with a high word:
  musl x86_64 struct semid_ds is 104 bytes with sem_nsems@80 (SDK
  bits/sem.h). Kernel wrote nsems@64 → userspace read __unused2.
  Fix: per-arch SemidDsUapi with compile-time layout contracts; the
  in-kernel layout test now asserts the per-arch contract.
  msgid64/shmid64 have no such x86 split (checked musl bits/msg.h,
  bits/shm.h) — untouched.
  Verified: semget01/semctl01/semctl07 2/2 rc=0 (sem_nsems == 10).

Bug 4 (process_vm EPERM/wrong data): REAL, fixed (ea40da3c).
  Root cause: ptrace.rs translate() was a third hand-rolled SV39 walk.
  On x86_64 it dead-ended (process_vm_readv02/03 EFAULT against a musl
  heap at 0x7ff000000000) or misdecoded a PML4 entry as a 1GiB SV39
  leaf and copied through WRONG physical pages — process_vm_writev02
  wrote 100000 bytes of corruption while reporting success. PEEK/POKE
  shared the same walk.
  Fix: PageTableWalker::walk, 4KiB frame semantics.
  Verified: process_vm01/readv02/readv03/writev02 2/2 rc=0.
  Note: the "-1 printed as EPERM" in readv02 was LTP's tst_strerrno
  label; the kernel actually returned EFAULT (EFAULTTRAC nr=270).

Bug 5 (rt_sigaction01 SIGILL at signal 35): NOT A KERNEL BUG.
  LTP's x86_64 sig_initial() trick reads oact.sa_restorer back from
  musl's sigaction(). musl NEVER fills old->sa_restorer (only glibc
  does), so the test installs an uninitialized stack value as the
  SA_RESTORER restorer; the handler returns into garbage and dies.
  Ground truth: the SAME musl-built binary booted on the real host
  kernel (7.0.0-31-generic, /boot copy) dies the same way — rc=139
  (SIGSEGV) at signal 35 (garbage restorer lands on an unmapped page
  there; on Rux it lands on mapped stack data → #UD/SIGILL rc=132).
  Rux matches reference behavior; no kernel change made. rt_sigaction01
  cannot pass with a musl-built LTP on ANY kernel (upstream test/
  libc limitation).
  Also verified en route: raw rt_sigaction roundtrips for signals
  32-64 are byte-correct (handler/flags/restorer/mask), musl-joined
  delivery + rt_sigreturn work for RT signals on x86_64.
