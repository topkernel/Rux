fio 3.36

Storage-I/O performance comparison (same image, same binary, same rig): throughput and latency; an engine row without numbers is unavailable · rig and method

§1Data (same image, same binary, same rig)

Both sides run the same ext4 image, the same static fio 3.36 binary, the same job file — Rux (main debug) and Linux (the host 7.0.0 kernel) in the same guest rig (q35/KVM/-cpu host/smp2/2G, virtio-blk); direct=1 bypasses the page cache. Each row carries its newest measured value; an engine row without numbers is currently unavailable.

Rows without data: libaio is an unimplemented UAPI (io_setup ENOSYS); io_uring's enter contract triggers a user-space crash (ring semantics incomplete). The posixaio engine runs; its throughput readings join the extension queue. The 48M job-size cap comes from the image's free space — the same constraint on both sides.

§2Rig and method

  • The pair: Rux (main debug) vs the Linux host kernel 7.0.0, the same QEMU q35 + KVM (-cpu host smp2/2G), the same ext4 image (reflink copy, booted snapshot=on), the same static binary (source tarball committed; built by userspace/fio/build-x86.sh).
  • Protocol: one boot per side runs all jobs in sequence (the qsrun cmds protocol); fio terse single-line output goes into the serial capture with the bw/IOPS/latency fields.
  • Basis: direct=1 rows are the real device path; the buffered-write row is the page-cache-absorbed basis (both sides); ratios are meaningful only within one session.

§3Extension
