§1Verdict: the lead/lag picture vs Linux

Every comparison against Linux on this page is same-host, same-accelerator: the same host (9950X), the same QEMU q35 + KVM (-accel kvm -cpu host), the same image shape, the same static benchmark binaries. No native columns.

📏lmbench same-rig: 14 of 21 cases ahead or at parity, 7 behind

Ahead: lat_pipe 4.6×, lat_ctx 2P 4.0–4.5×, lat_ctx 8P 3.6×, bw_pipe 3.7×, lat_sem 2.9×, bw_unix 2.1×, lat_unix 1.4×, fstat 1.3×; bcopy/bzero/mem_rd/usleep at or above parity, bw_file_rd faster than the timer granularity.

Behind (Rux/Linux): open 1.92×, read_cached 1.84×, stat 1.28×, write 1.06×; null now at parity (0.97×); fork/exec 0.75–0.79× (ahead). Storage and real-time rows below.

best lead 4.6× · worst lag 2.5× · data on the lmbench page

⚡Storage and real-time rows: phase-probe attribution, reference-shaped rebuilds

Storage I/O was attributed with a phase probe (per-op cost split into interrupt delivery, dispatcher polling, softirq hop, wake-to-resume), then rebuilt along the reference kernel's shapes: the direct path submits physically consecutive runs in one request (1M sequential read from 226× behind to 2.0× behind, sequential write from 57× to 2.5×), MSI-X with completions walked inside the hardirq vector (4k random read 0.27× to 0.77×), journal commits write through in batches (fsync halved vs main), directory reads fill incrementally (getdents from 19× behind to 1.95× ahead), path/descriptor costs and leaf-table reclamation (stat 1.28×, openclose 1.92×, read_cached 1.84×, fork_exec 1.72×). Real-time: timer expiry moved to the top of the hardirq vector (rt_wakesys 3.3 µs, parity), PI futex follows the reference rt_mutex_setprio shape (pi_stress 132,074 inversions).

Per-item rows: fio and rt-tests · method and evidence: docs/test/perf-campaign-2026-11-17.md

🏁Geekbench 5: single-core 2440 / multi-core 7709 (historical best)

Single-core total 2440 vs 2165 (113%), multi-core total 7709 vs 7027 (110%), best-of-runs convention (gb-opt round, 2026-11-15). Per-workload split from the 2026-11-04 full capture: multi-core 8 ahead / 5 parity / 8 behind; single-core 13 ahead / 3 parity / 5 behind.

per-workload on the Geekbench page · rig note: Linux side is the host 4-CPU pin (taskset, topology-matched)
Gap structure: the leads cover scheduler/wakeup (context switch, pipe, semaphore), IPC bandwidth (unix, pipe) and memory bandwidth; the remaining gaps concentrate in syscall entry and path resolution (null/read/write/stat/open at 1.2–2.5×). Under the older reference window the historic campaign had scored fork/exec at parity; the 2026-11-16 same-rig re-measure puts them in the 1.08–1.19× band (the reference kernel's switch family is measurement-window-sensitive — ratios are only meaningful within one session). The 5 correctness bugs the campaign found and fixed are listed after the §2 tables.

§3Method and rig

  • Same host, same accelerator: both sides on the same host, the same QEMU q35 + KVM (-accel kvm -cpu host), the same Ubuntu rootfs shape, the same static benchmark binaries; one case per boot (the serial console interleaves with long sweeps, so a single-case boot is the only clean collection), PID 1 runner, 35 s in-guest budget (exceptions noted per case).
  • Comparable-class rule: debug vs release-strong never cross-compared (strong reads 10–30× lower on the floor families); TCG vs KVM never cross-compared.
  • Anchor provenance: gate anchors read only Rux's own medians — the Linux column never enters a Rux gate anchor (leg 32 found four cells transcribed from the Linux column; corrected and filed).

§4The merge-gate performance dimension (three tiers + six domains)

Every merge is reviewed for both function and performance; baselines move only through merges that passed their own tier; a regression blocks the merge until fixed or justified in writing. Workflow details: Contributing §3.

§6Optimization queue (open gaps, priority order)

  • COW-fault cross-CPU shootdown: the +58% (18.42 µs) honest gap at SMP-8, affecting fork-heavy service graphs — the next main target.
  • lat_syscall open 1.61× / stat 1.32×: open's tail (memo-hit 80–90 ns + fd install); stat's tail v3 unblocked now that the call_rcu contract is fixed — retry.
  • lat_syscall null 1.18× / write 1.14×: entry floor; null's 2× is proven physically unreachable (the shared syscall RTT floor) — converge to parity; write is 6 ns from parity.
  • Geekbench single-core residuals: Text Compression 94% / Navigation 81% / PDF 85% / Clang 88% / Face 87% await isolated re-runs (AES-XTS root-caused and fixed, 105–106%; single-core best-of-runs 2440 = 113%).
  • Network family: bw_tcp TIMEOUT / lat_connect 14–16 ms — a scheduler stale-claim refuses the accept server/worker wakes (WAKE-HEAL-SKIP ×39); TCP throughput needs that fix first.
  • Backfill queue: a fio throughput benchmark (same-rig Linux baseline, direct=1); the Geekbench same-rig KVM comparison; page-cache hit-rate absolutes, PCP watermarks, binder throughput.

§7debug measurement toolchain

  • syscost: boot census (syscall volume, census counts, tick rate, per-op averages) — the Tier 1 collector.
  • pbench (test/pbench.c): the P1–P7 microbenchmark probes — the Tier 2 collector.
  • census / wakewatch: scheduler-stall census (WAKE-STRANDED) and wake→run latency forensics (1024-slot side tables + pick-skip reason table).
  • if0 v3: EFLAGS-pair probe — the official IF=0 share and cli-segment measurement (on main; no more tick-mode proxy).
  • fsw / mmprof counters: fs sync-write classes, memory accounting reconciliation (OOM forensics).
  • run/perf-gate.sh: gate automation (anchor JSON + tier dispatch + band verdicts).
  • Unified tracepoint framework: 69 events / 17 groups, byte-exact tracefs, +13–19 ns per record when enabled (see Observability).
