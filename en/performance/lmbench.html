§1lmbench data (same-test platform KVM, 21 cases)

Source: the "Standing (2026-11-16, kernel main=017bf556b)" section of lmbench-report.md — the single authoritative table; the data below is that section. Method: both sides in the same test platform (q35/KVM/-cpu host/smp2/2G, host CCD0 pin + performance governor + warmer thread); Rux boots with nohz_full=1, one case per boot with the retry rule; the Linux column runs the OHOS 6.6.101 kernel in the same guest test platform with the same static binaries, 2 reps, medians. The switch/wakeup family is sensitive to the Linux-side measurement window — ratios are only meaningful within one session.

Basis: each row carries the latest measured value on current main (the 2026-11-16 full round; the null/read/write rows re-measured 11-17). The Rux column follows each round's own build class; the Linux column = the host 7.0.0 kernel booted in the same guest test platform running the same static binaries.

Notes: the bw_file_rd and lat_pagefault rows carry values recovered after the image-runner fix (the earlier lows were not trustworthy); the lat_syscall null flip comes from the fdget borrow + getppid O(1) + PT_REGS + fdreap silence + the NOHZ stack. Mechanism note: the wins concentrate in scheduler/wakeup and IPC (cross-vCPU wakeup IPIs are expensive under virtualization; the single global run queue produces no cross-core reschedule storm) and memory bandwidth; syscall-latency rows run the guest's own entry (no vmexit), so the gaps there are real kernel differences. Rows without honest numbers: bw_mmap_rd and the net-server family (lat_tcp/udp/connect, bw_tcp, lat_fs) — not listed; lat_mmap 4.525 µs (1.12x vs ceiling, near-parity band).

Correctness bugs the same round found and fixed (the performance gaps were hiding them): a stale-rsp0-at-free UAF (the fork bistability root cause); a call_rcu zero-grace callback firing; a wake-monitor staleness inversion; the fdreap per-tick 10 ms close stall; the mainline munmap final-TLB-flush loss (5b4a4bc7).
Why the large leads: design trade-offs, not missing safety features.Code-level argument, item by item:
(1) Source of the wake/switch family gap (sem 8.97x / ctx-8 6.29x / ctx-2 5.14x / pipe 5.84x) — the reference's per-CPU runqueues under KVM make every ping-pong roundtrip pay cross-core resched IPIs (vmexit + halt-exit, 2-5 µs each; the IPI send side alone measured 935-1139 ns). Rux's single global run queue (register D-1) plus the 120 µs polling idle window turns µs-scale handoffs into same-core, ZERO-IPI transfers (sched/sched.rs idle window, closegap lane measurements). This is queue topology winning under virtualization's cost structure.
(2) The safety machinery is fully present on exactly these paths: the polling window's lost-wake impossibility is by protocol (flag-clear + SeqCst fence + recheck Dekker pairing, sched.rs idle loop); every enqueue carries wakewatch forensic stamps and schedstat wait accounting; all GRQ mutations run under the INV-LOCK-* lock discipline; RCU quiescent-state reporting runs at BOTH syscall entry and exit (sync/rcu.rs).
(3) User-memory access safety matches the reference shape: every uaccess (scalars included) goes through exception-table fixups (arch/x86_64/uaccess.rs) — bad pointers return EFAULT, never crash. x86 SMAP is currently not armed (honestly recorded, sec-r1), but its performance contribution to these cases is ~2 two-cycle instructions per copy (~1 ns) — 0.005% of the pipe gap's 20 µs scale — not the source of the lead; the semantics are preserved by the active exception-table path.
(4) fork/exec copy-on-write and teardown safety present: fork's mmfork phase carries the full PTE write-protection (COW, per the forkprof decomposition); page-table freeing goes through an RCU grace period; fd lifetimes go through the retire queue (fs/fdreap.rs).
(5) The bug taxonomy corroborates: every memory-corruption-class historical bug lived in audited unsafe code, zero in safe code (docs/architecture/safety-and-performance.md §2). The full lead list with measured evidence: docs/architecture/rust-native-register.md (D-numbers and same-test platform A/B figures).
