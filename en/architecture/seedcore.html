The Seed-Core architecture

A minimal trusted core + every other subsystem as a compiler-guaranteed-safe service crate · the one criterion, the dependency direction, the four stay rules, the three call forms, interface design rules, the irreducible floor, the three-layer defense, the industry landscape, the S1 case study, the measured size, and the landing status · design of record: docs/architecture/seed-core-design.md · interface rules: docs/architecture/crate-plan.md §3a · landing status as of 2026-11-23

Naming (2026-11-22): Seed-Core / 晶核, the materials-science metaphor: the ~3,000-line hand-written core is the seed crystal; every service line crystallizes into safe code on the type-system lattice (the forbid attribute + borrow checking); the compiler is the crystallization condition. The seed is tiny yet determines the integrity of the whole crystal. The name deliberately distinguishes from the microkernel (address-space isolation, an IPC boundary of ~1,000 CPU cycles per cross-service call) — Seed-Core has no address-space boundary at all (§8). This page is the full expansion of the design document, whose status is design of record (2026-11-22, user directive: "shrink the TCB to the minimum; ideally every subsystem becomes a crate and is safe"); it supersedes the end-state section of crate-plan.md, whose extraction mechanics (the five-step migration recipe) remain binding. Execution follows the stage order; nothing lands out of order.

§1The one criterion and the size directive

The kernel's end state is one small trusted crate plus forbid-enforced service crates. The criterion for every line of code is a single question:

Can this code live under #![forbid(unsafe_code)]?
  • YES → it belongs in a service crate (compiler-guaranteed safe).
  • NO → it belongs in rux-core, carries an INV contract or F-row, and is covered by the verification stack (Kani/Miri/Verus).

There is no third bucket for unsafe. "Framework" as a catch-all for leftovers is abolished: what remains in the core is there because it cannot be safe, not because it was not yet converted.

Terminology (defined at first use).TCB (trusted computing base): the set of all code on which the kernel's safety properties depend — any defect inside the TCB can break those properties; the smaller the TCB, the smaller the surface that must be audited line by line.forbid (the crate-level prohibition attribute): with #![forbid(unsafe_code)] declared at the top of a crate, any unsafe code in that compilation unit is a compile error (adversarially verified: injecting unsafe into a service crate must fail that crate's own build), and the attribute cannot be downgraded to a warning or disabled by modules inside the crate.INV contract: every unsafe block retained in the core carries a numbered machine-verifiable precondition declaration. Example — INV-SCE-3 states: "the global run queue's storage is written exactly once by grq_init under the GRQ_READY flag's CAS; subsequent reads occur only after that flag's Acquire barrier" — specifying the memory-visibility condition the unsafe block depends on for correctness.Each declaration answers three questions:what precondition must hold for the code to be correct(e.g., "this page is mapped and aligned"),what constraint must not be violated during execution(e.g., "must not call any function that may free this pointer while held"), andwhat cleanup is mandatory on exit(e.g., "must release the reference count").Registered in docs/architecture/safety-and-performance.md, one-to-one with the code.F-row: for unsafe code argued non-rewritable in safe Rust (e.g., the context switch must manipulate CPU registers directly, beyond the safe subset of the language), a row in the irreducibility register records: owning function, line count, why no safe rewrite exists, and the counterpart in the reference implementation (e.g., Linux's entry.S).Together: every unsafe line among the ~3,000 core lines has an audit entry, 97%+ coverage.

The size directive (2026-11-23)

The criterion above settles where UNSAFE lives. It did not settle how much safe code stays in the core — and by 2026-11-23 the answer was "most of it": kernel/src held 286,139 lines with 1,838 unsafe blocks and 238 unsafe fn/impl bodies. The directive for the rest of the campaign:

The core's code should be as small as possible, as long as performance is unaffected. Code that leaves the core is organized by subsystem.

The following sections answer the three questions that follow from it: why the core must not depend on a service crate (§2); which code has to stay (§3); and what a call pays to cross the crate boundary (§4).

§2The dependency direction: why the core must not depend on any service crate

The rule "services depend on the core, never the reverse" is usually justified by the build graph. The real reason is what it does to the argument that the core is correct.

The core maintains the kernel's data-structure invariants: the task-slot life cycle, the run-queue locking protocol, atomic page-table updates, reference counts. To argue that an invariant holds, one has to know everything that can change the state it constrains, in what order, and under which lock.

If the core called a service crate directly, that argument would not close. To show that __schedule() preserves the run-queue protocol one would have to follow the call into the scheduler policy crate — and that crate changes with every wake-up or load-balance edit; each edit could remove a premise the core's proof relied on. The core's trusted computing base would then be its own code plus every line it can call, a set that grows with the service crates and has no fixed boundary.

With the dependency pointing the other way, the core reaches a service only through a callback table (the core defines each slot's function signature; the service registers its implementation into the table at boot). A row such as pick_next_task: fn(&CpuRunQueue) -> TaskRef states what the callee is able to do: read the run queue, return a task reference. It cannot reach the lock's internal state, alter the queue's structure, or touch a context that is being switched — not because its code was reviewed, but because the published types do not express those operations. The core's argument becomes closed: whatever a callback does, it acts only through the interfaces the core publishes, so the core's invariants hold independently of the service crates' contents.

core depends on a cratecore depends on nothing
the core's trusted computing basethe core plus every line it can callthe core alone
after a change to a service cratethe core's invariants must be re-arguedthe core's argument is unaffected
the invariants rest onthe service code happening not to interfereinterfaces that cannot express interference

The callback table is therefore not only an indirect-call layer with a performance cost (§4, the S1 case in §11); it is the machine-checked statement of the service's entire view of the core. It also answers why hot-path FIELDS stay in the core (§3, rule 3): a field that a hot path updates under the core's lock protocol must not be reachable through any type a callback can obtain — otherwise the callback could change it outside that protocol.

§3The four stay rules

Four things force code to stay; everything else can leave.

  1. A function a hot-path site calls by name. Hot-path sites are the trap entry and return, the context switch, the page-fault path, the VFS walk, bio and the page cache, the allocator entry points, the lock primitives, the timer tick, IRQ dispatch. After a move, that call would have to go through the callback table — an indirect call the compiler cannot inline (a function pointer's target is a runtime value). The function stays where the hot caller reaches it directly.
  2. A function an existing service crate calls by name. A service crate reaches the core, not another service crate (a lateral edge is a dependency between subsystems that Cargo would have to order, and a cycle is refused). A function rux-syscall uses therefore has to be in the core. Example: restore_sigcontext, called from sys_rt_sigreturn — the case the signal lane found on 2026-11-23.
  3. A field a hot path reads or writes directly. This is a constraint on FIELDS, not on types. A service crate uses a core-defined type freely (service → core is the allowed direction); what must stay is the set of fields the hot paths touch, because Cargo forbids core → service. Measured on Task (105 fields):
hot pathfields touchedfields
context switch7thread, kernel_stack_bottom, address_space, state, pid, on_cpu, pick_state
trap path10pt_regs, address_space, kernel_stack_bottom, preempt_count, sigmask, pid, tgid, utime_ticks, stime_ticks, comm
scheduler6ti_cpu, ti_flags, state, sched_entity, rt_entity, pid

About 20 in all. The other ~85 (ptrace state, robust list, syscall/exit/reap bookkeeping, statistics) are never read on a hot path. Such a type can be split into a core block holding the hot fields — same offsets, same cache-line neighbours as today — and a service block reached by one pointer the hot paths never follow. That costs the hot paths nothing: every field they access is still in the core block at its present offset. The split is structural work across every subsystem and comes AFTER the function-level moves; until then a type with any hot field stays whole, and its cold METHODS leave as free functions.

  1. A function that is unsafe and on the F-row floor — pt_regs writes, building the signal frame on the user stack, the switch itself. No name-based scan sees this; the lane that owns the function keeps it and records why.

Everything else leaves. A function that neither a hot path nor a service crate calls is reached only from cold sites, and a cold upward call through the table is acceptable. The moved code's own calls INTO the core are direct cross-crate calls that inline. §4 gives the complete asymmetry table for the two directions.

§4The three call forms: how a call crosses the boundary

Every question about whether moving code costs performance reduces to how the call crosses the crate boundary. Three forms exist in this kernel; the campaign's placement rules follow from them.

A direct call names its callee. mm_edges::zero_range(...) — the compiler sees the target, checks the signature, emits a call with a fixed address. Between crates nothing changes: the callee's MIR travels in the rlib metadata, so the optimizer can inline across the boundary exactly as within one crate, and LTO makes it certain. A direct call is therefore free wherever the dependency points the right way — a service crate calling into the core pays nothing, no matter how hot the site.

An indirect call reads its target at run time. A function pointer loaded from the callback table:

// the core's dispatch site
let next = (hooks.pick_next_task)(&rq);

The compiler cannot know which function the slot holds — it is a value published at boot — so it cannot inline, cannot constant-fold the arguments, and must keep the call clobbering the full caller-saved register set. Each indirect call costs a few nanoseconds by itself. The real cost is what it disables, multiplied by the call frequency: everything the callee would have done under the caller's knowledge (argument specialization, dead-code elimination across the pair) is lost for every site. The S1 measurement (S1 = the scheduler subsystem's mechanism/policy split, §10) is the record: ~40 diagnostic rows fired per context switch, each one indirect, and the switch median moved +25.1% (1.718 → 2.149 µs); moving the statics framework-side so the same sites called directly brought it back to +1.7% (the full record in §11).

An interface method (a vtable field) is an indirect call the caller already pays. ops.fault(file, off) on a FileOps reads one field and calls it. This is not a new cost — the call was virtual before the move and virtual after — so moving a leaf implementation behind its existing FileOps slot adds nothing. That is why the ext4 migration put the read/write paths on FileOps.fault / FileOps.write_at instead of adding table rows.

The asymmetry of the two directions, in one table:

Two properties of indirect calls decide the layout, not taste: (1) inlining requires the callee to be a compile-time constant, which a table slot never is; (2) the cost multiplies by call frequency — negligible on cold paths and measurable on hot ones. The same row can be free in one subsystem and a 25% regression in another.

§5Interface design rules: what makes the closed argument true

The closed argument in §2 holds only if the published interfaces actually express the constraint. A callback typed fn(*mut Task) gives the callee the whole task through a raw pointer and guarantees nothing; the table would be a formality. The rules that make the boundary real:

  • Types carry the precondition. The core publishes typed handles (TaskRef, TaskBorrow, Arc<T>), not raw pointers. A service that needs the file's private data calls fs::unsafe_edges::file_privdata_take_arc::<T>(file) -> Option<Arc<T>>; the borrow checker keeps working on the result. It cannot write unsafe { &*p } — the crate forbids it — and it has no p to write.
  • Visibility is the boundary. Inside one crate, pub(crate) is reachable from everywhere. Across crates, a service sees only what the core marks pub, and a pub item is a deliberate publication with a name, a signature and an INV contract. When the filesystem code left moved into the forbid crate (2026-11-23), their scattered raw-pointer accesses had to converge on a handful of typed functions in unsafe_edges.rs: the accesses did not disappear, they became a short, enumerable list that can be audited one by one.
  • The hot path never calls into a service crate through the table (crate-plan §3a rule 2): an interface on a data path takes an existing vtable field (FileOps.fault, FileOps.write_at — field dispatch the caller already performs) or a direct #[inline] wrapper over a framework-side static, never a new fn-pointer row. Table rows are for cold paths and may be skipped at the call site when the instrument is not enabled.
  • The table is the service's whole view. A service reaches the core only through published functions and the rows it is handed. If a service needs something the table does not offer, the answer is to add a typed core function or a row — not to widen a type's visibility, and never to let a row's body call the wrapper that dispatches that same row (the self-recursion that stalled the scheduler migration).
  • Nothing that runs before the per-CPU area exists may take a lock. Every Spinlock::lock() here reads per-CPU state (the preempt count, the holder's cpu id), which on x86_64 is %gs-relative with the GS base still 0 during rust_main. Registration at that point publishes through OnceSlot or a plain atomic. The first version of the service-test registry took a Spinlock there and the x86_64 unit-test kernel faulted before its first print (2026-11-23).

The three cross-crate interface rules (crate-plan §3a, adopted 2026-11-23)

Three rules for designing any callback table or trait interface — the same principles the in-tree Rust leaf work in the reference monolithic kernel uses to keep its FFI-adjacent abstractions cheap. We derived them independently (paid for with measured regressions), and they are binding for every future migration:

  1. Split by concern, never a mega-table. One table per lifecycle/consumer (the fs side has MountFn / notify / ops / relocation / FsHooks as five separate tables; mm has MmHooks vs MmPolicyHooks). A table whose rows exceed ~20 must either split or justify its width in the interface's doc comment.
  2. Static dispatch first on hot paths. An interface on a data path takes an existing vtable FIELD (e.g. FileOps.fault / FileOps.write_at — field dispatch the caller already performs) or a direct #[inline] wrapper over a static, NOT a new fn-pointer row. Receipts: S1's ~40 indirect calls per switch cost p2_ctxsw +25.1% until devirtualized to +1.7%; R5's read/write paths ride FileOps slots at zero new indirection. Fn-pointer table rows are for COLD paths (mount rows, procfs show, sysctl, exit/exec hooks) and may be arm-gated at the call site when their body is diagnostic.
  3. Thin mechanical adapters. Interface signatures carry the native error type (Result<_, i32> errno or the domain enum) and the adapter layer contains ZERO logic — bodies move verbatim; conversions are one line and mechanical. If an interface body needs logic, that logic belongs on one side of the boundary, not in the interface.

§8Why not address-space isolation: the microkernel comparison

The classic way to buy fault isolation is separate address spaces per service (seL4/L4 family): a bad driver cannot corrupt kernel memory because it cannot address it. The price is the boundary — every cross-service operation is an IPC through a context switch, ~1,000 cycles on the best fastpaths, multiplied along fault→driver→server chains (the Mach lesson; L4's fastpaths recovered much but not all of syscall-heavy paths).

This design buys the SAME memory-safety property statically, at zero runtime cost: a #![forbid(unsafe_code)] crate cannot express a wild pointer, use-after-free, or data race — the Rust type system provides what address spaces provide in a C microkernel, without a runtime boundary. Cross-crate calls are plain function calls (LTO inlines; the M3 migration verified zero behavior change with the dispatch tables live). This is the RedLeaf/Framekernel line: language isolation without address spaces, keeping the hardware backstop (§7) instead of betting everything on the type system.

What remains true for both designs: logic bugs (deadlocks, wrong decisions, leaks) pass through; only memory-safety classes differ. A microkernel spends ~1,000 cycles per boundary to buy layer (1); this design buys (1)+(2)+(3) for 0+~50+0.

§9The four industry Rust-kernel families, and Seed-Core's position

Industry Rust kernels answer "where does unsafe live, and how is the TCB drawn" in four ways. Seed-Core (defined in §1) is not one family carried to an extreme — it COMBINES the specific strengths of several of them and hardens the one thing none of them machine-checks.

  • Family 1 — microkernels: Redox, Tock, Hubris. Redox is a MINIX-inspired microkernel (~16,000-line kernel; drivers and services run in userspace, isolated by the MMU). Tock targets embedded: a minimal trusted kernel with drivers compiled in as "capsules" written in Safe Rust, user processes protected by the MPU — at the price that every added capsule grows the TCB (measured TCB share ~43.8%). Hubris (Oxide) assigns all tasks statically at build time; kernel, drivers, and tasks live in separate protection domains enforced by hardware memory protection. Common position: isolation by HARDWARE (MMU/MPU), a tiny kernel, and an IPC cost on every cross-component call.
  • Family 2 — the framekernel: Asterinas (the closest relative). A framekernel (the term comes from Asterinas, USENIX ATC'25) splits the kernel LOGICALLY into a Framework (the only zone allowed unsafe) and Services (all Safe Rust), in ONE address space and privilege level — service calls are plain function calls, no IPC overhead. Measured: TCB share ~14.0% (vs Tock 43.8%, Theseus 62.4%, RedLeaf 66.1%); LMBench geometric mean 1.08x of the reference monolithic, Nginx 1.17, Redis 1.31. This is structurally the same mechanism/policy split our design implements — the difference is that Asterinas' Framework is a LOGICAL layer held by convention and review inside one crate, while we draw the boundary on the CRATE COMPILATION UNIT and let the toolchain check it. That is a difference in enforcement hardness, not style.
  • Family 3 — leaf-style: the in-tree Rust leaf work in the reference monolithic. No kernel rewrite: scheduler, mm, VFS, and RCU remain C; Rust lives in the leaves (drivers, file-system modules, binder-class subsystems). The unsafe boundary is the safe wrapper set the kernel crate exports; underneath it is FFI into C. The TCB is the ENTIRE C kernel — the Rust-side guarantees cover only newly written leaves. Its reference value for us is not architecture but ABSTRACTION CRAFT: deliberately minimal traits (FileSystem, Operations, INodeOperations kept separate rather than one 50-method mega-trait), static dispatch preferred over trait objects, thin mechanical error mapping. We use exactly these techniques to keep our indirection costs low.
  • Family 4 — single-address-space cells: Theseus. One address space, one privilege level; the thesis is "intralingual design" — hand as much OS bookkeeping as possible to the Rust compiler itself — with components as crates ("cells") that can load dynamically, to avoid state spill (persistent state changes caused by component interaction that make fault isolation and live update hard). TCB share ~62.4%, higher than Asterinas because more stays trusted. Theseus explicitly justifies the single-address-space, single-privilege model as matching the Rust compiler's execution model — an independent endorsement of our mechanism-stays-in-core decision.

What Seed-Core takes from each family, and what it adds. From the microkernels: the discipline of a minimal trusted core — our floor is itemized line by line, each entry with a reference counterpart and an F-row id, not a zone. From the framekernel: the single address space and the zero-IPC boundary — cross-crate calls are plain function calls, LTO-inlined, a full protocol layer thinner than RPC; where an interface's indirect-call cost surfaced, we engineered it away (context-switch +25.1% recovered to +1.7% by devirtualization) rather than accepting it. From Theseus: the crate as THE isolation unit, and the single-address-space execution model as the one the compiler itself understands. From the leaf-style work: the minimal-trait, static-dispatch, thin-error-mapping craft that keeps our hook tables cheap. And no other Rust kernel puts the boundary in the BUILD SYSTEM — Asterinas included: per-crate #![forbid(unsafe_code)] makes unsafe in service code a COMPILE ERROR, not a review finding (negative-probe verified); Cargo's package DAG refusing dependency cycles makes layering violations BUILD FAILURES; a CI ratchet on the attribute set means removal fails the build; behind the type layer an MPK hardware backstop (WRPKRU at 47–49 measured cycles, fault-injection proven). A logical layer erodes by convention; a build error cannot be written. That is the claim: monolithic-class performance, a TCB smaller than every measured share above, and the only boundary in the space defended by the toolchain rather than the process.

§10Mechanism/policy separation (S1/M1): the classic principle, compiler-enforced

S1 is the first compiler-enforced implementation of MECHANISM/POLICY SEPARATION (the classic operating-system design principle). The MECHANISM — the low-level state-changing operations: context switch, the global run queue's locking protocol, the current-task pointer's register read, task-slot allocation and reclamation — directly maintains the kernel's data-structure invariants and stays in the core crate under line-by-line audit. The POLICY — the decisions built on the mechanism: which task runs next, which CPU a wake-up is placed on, when to throttle — accesses data only through the mechanism's type-safe interface and moves to a separate service crate under forbid. Traditionally this separation was maintained by code review alone; here the compiler statically guarantees it: any unsafe use in policy code is a compile error. The callback-function table and the private-interface API constitute the mechanism's complete calling contract published to the policy. M1 applies the same separation to memory management.

§11The S1 case study: the interface-cost regression and its fix — BOTH guarantees held

S1 landed with a performance regression that the merge gate refused to wave through; its resolution is the standing proof that this design guarantees safety AND performance together — neither is traded for the other. The record, with numbers (p2_ctxsw is the context-switch row of the pbench microbenchmarks):

  1. The regression. After the migration, pbench p2_ctxsw read 2.149 µs against 1.718 µs on same-window main (+25.1%) — outside the ±20% scheduler guarded-domain band. The merge was held until fixed (gate policy: functionally correct but performance-regressing does not merge).
  2. Root cause — NOT "cross-crate calls are slow". Direct cross-crate calls inline fine (rlib metadata carries MIR; LTO completes it). The cost was the DISPATCH MECHANISM: upward calls (core→policy) ride a registered function-pointer table, and a call through a function pointer is indirect — the callee is a runtime value loaded from the table, invisible to the compiler, NOT inlinable by LTO or anything else. The first SchedHooks table exposed 111 rows, and observability dominated: per context switch ~40 rows fired (sched_cs_stamp ×4/schedule, pick_trace ×2–3/switch, pick_gen publish/retire, ww_record, wake census, vr_canary, class counters), each paying shim → wrapper → slot load → indirect call. At ~10 ns each in the debug class that is ~400 ns — the measured delta (431 ns) to within noise.
  3. The fix — make the hot calls direct again. Three moves, no behavior change: (a) the 33 observability rows LEFT the table — their statics now live framework-side (entities.rs) and the framework calls them as direct static calls, which inline; counters record identically. (b) The genuinely dynamic dispatch collapsed to ONE fat entry: pick_next_task — the whole pick walk runs policy-side inside a single crossing, not one crossing per step. (c) The three conditional diagnostic rows became arm-gated wrappers (the wrapper checks the same framework-side flag the body checks; disarmed boots never touch the interface). Armed-mode output verified byte-identical (the exact 40-line WWTICK budget).
  4. Result. p2_ctxsw 1.758 vs same-window main 1.728 = +1.7%, in band; P4 storm rows +2.6%; zero panics across 10 measurement boots + the armed boot; rux-sched's forbid untouched — the fix cost ZERO unsafe: it moved plain-safe state and reshaped call sites. The SchedHooks table went from 111 rows to 78.
  5. The rule extracted (crate-plan §3a, binding for every future interface): fn-pointer table rows are for COLD paths only; a hot path takes (a) the whole loop behind one fat entry so the boundary is crossed once, (b) an existing vtable FIELD (FileOps.fault/write_at — field dispatch, R5's read/write paths at zero new indirection), or (c) direct static calls over framework-side statics. Observability statics live framework-side by default.
The lesson stated once, plainly: the crate boundary's safety is free; the DISPATCH MECHANISM is what costs. Design the interface, measure it, and if it regresses, fix the interface — never the safety property.

What this does and does not guarantee

Honest limits, so the claim is not read for more than it is worth. Two terms defined first: the audit record is the record that maps every unsafe region to its INV contract or F-row; the published surface is the set of functions and types the core marks pub for the service crates.

  • The dependency direction does not make unsafe impossible; it makes the service crates' zero-unsafe REAL. #![forbid(unsafe_code)] alone is bypassable — a crate that may not write unsafe can call one that may. Because the core depends on no service, a service cannot reach any code that writes unsafe except the core's published functions.
  • Service code can still call those published functions, some of which are unsafe inside. The guarantee is that every such call passes through a named, typed function with an INV contract, and those functions are the only way across — not that service code can do no harm.
  • A function having a contract does not make the contract correct. On 2026-11-23 the audit of that record found that 349 of 1,591 existing annotations contradicted the code they described. The audit freeze (the final step of §14's order) is where the published surface is checked function by function: whether each signature states its precondition or merely documents it.
  • The core that remains is still a trusted computing base. It is now bounded, named, and unable to grow silently; it is not exempt from the INV/F-row discipline or the verification stack.

§14Execution order, shelving discipline, and open items

The execution order is binding; each stage = measure → design the interface → migrate → forbid → test set:

  1. R1 close (in flight): syscall State B — delete the in-lib files, full test set, negative probe. Gates: triple-arch, make test, fio 3-case, smoke; the census columns begin.
  2. S1 measure (next): sched policy/core edge count (one day, no code). Then interface design → policy crate migration → forbid → test set (incl. the P4 storm + ctxsw pbench — a guarded domain). Completed as such (§13).
  3. M1 measure: mm policy/core edges. Then as S1 (test set incl. the defect-C pair + mmap LTP rows). Completed as such (§13).
  4. R2 net: the measured 35-site relocation + migration.
  5. R3 fs-svc + R5 ext4: the biggest mass; measured per crate-plan.
  6. R4 drivers: the last service stage.
  7. debug review: per-instrument adjudication — hunt closed → the instrument retires (delete); hunt alive → the instrument moves to rux-debug-svc behind its flag. Phase 1 landed (r83hunt and treehunt deleted with their call-site stubs and gate events; −915 debug/ lines); the KEEP families carry written exit criteria.
  8. Core audit freeze: the final INV/F-row registry pass — every core line under a row; the per-block irreducibility proof (the D-round deliverable) then covers exactly rux-core. This is where the 349/1,591 contradicted annotations of §12 are being found.

Every stage's gates: the standing set (triple-arch build, make test, unsafe_gate, print ratchet, smoke) + the stage's domain test set + the forbid negative probe at crate scope. A stage that fails its test set twice halts the order (no piling changes on an unstable base). Shelving is success, not failure: a measured non-decomposable surface keeps that subsystem core-side with its numbers recorded in the design document.

What happens to the edges files

The per-subsystem edges.rs/unsafe_edges.rs files dissolve by stage: each of their functions is either (a) a call into a core primitive — the edge fn becomes a thin re-export and then dies — or (b) genuinely local unsafe — it MOVES into rux-core under its INV row. At the end state there are no per-subsystem edges files; there is the core's registry.

Risks and honest limits

  • The core is still ~3,000 lines of hand-written unsafe. The design minimizes it to the reference kernel's own floor class; it does not eliminate it. The verification stack is the compensating control.
  • Policy/core interfaces can be wrong (the defect-C lesson: interfaces between lock domains are where races live). Each split's interface gets the fault test set, not just the suite.
  • Hot-path cost: policy-in-crate means cross-crate calls on scheduler and fault paths. Mitigation: LTO + inlining across the workspace is already the build shape; the ctxsw/fault pbench rows gate each split (§11 is the instance).
  • Shelving is success: a measured non-decomposable surface keeps that subsystem core-side with its numbers recorded (vma + mm_struct, binder.rs, sysv_sem — §13).
