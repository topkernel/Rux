What Rux is

A Linux-ABI-compatible operating-system kernel written from scratch in Rust · 679 files / 419,958 lines under kernel/ (408,864 of them Rust) · 349 system calls · LTP 1,139/1,869

§1Why I wrote a kernel myself

The Rust kernels that exist are usually one of three things: a teaching kernel, a microkernel prototype, or a compatibility claim expressed as a syscall-coverage number. What I want is concrete: the performance floor of a monolithic kernel, the Linux ABI as a binary contract, and Rust's auditable safety. All three, none optional.

Hence Rux. The code is public, and this page simply states what I built, how it is built, what the code looks like, and which parts are not finished.

The starting motivation is equally concrete: I ran a dozen agents in parallel on Ubuntu and the typing latency reached one to two seconds, which was not acceptable — rather than keep tuning someone else's kernel, I wrote my own. That motive decided the trade-offs that followed: the scheduler is a single global run queue (GRQ), designed by subtraction for personal devices with 8–16 CPUs, where it removes load migration and task stealing; a server kernel was never in scope.

§2ABI compatibility: not "how many syscalls", but "boot it"

My design principle in one line: the ABI is the contract; the internals are free.

Outward, everything userland can observe is contractual — syscall numbers and semantics, ELF and auxv, futex, POSIX and SysV IPC, binder, on-disk ext4, the procfs/sysfs/debugfs/tracefs layouts, down to the uname strings glibc's dynamic loader keys on. The current implementation has 349 system calls on the asm-generic table (the x86_64 native numbering translates onto the same table), and a full LTP scan of the 1,869-case list passes 1,139.

Inward, no constraint from the mainstream's internal history. Every internal design that differs from the common approach is written down with its compatibility evidence — 29 registered design divergences at present (the divergence register).

The verification method matters more than the count. A curated syscall subset proves nothing; unmodified distribution images prove everything:

No patches, no recompilation, no configuration changes. Syscall coverage is a number; an end-to-end boot is a fact.

§3AI-written code is an engineering method, not a slogan

I expect this one to be contested, so let me be precise: Rux's subsystems — scheduler, memory management, ext4, binder, the network stack, the verification harness — and all of the code, documentation and this site were written by AI. The human role is goal-setting, review and merge.

The working model: parallel agents, each with its own git worktree and branch, with the main session reviewing and merging; several merge rounds a day, each preceded by a full regression pass. About 200 worktrees are live at the moment. Merging has exactly one gate (AGENTS.md): three-architecture build, the full in-kernel suite, tiered performance gates and data-integrity checks — a change lands with all of them or not at all.

This is not "an assistant filling in a few lines". It puts AI where subsystems get implemented and keeps the human at architecture review and the merge gate. Whether that model holds at 400,000 lines is still under observation. So far it has produced a complete kernel that boots a desktop from a real distribution.

§4Safety: not "Rust is safe", but the itemized bill

"Rust is safe" is a sentence everyone has heard too often. What is actually worth knowing is: what has gone wrong inside unsafe code, and how I manage it.

How large the unsafe surface is. kernel/src is 364,401 lines. Measured by the in-tree ledger script:

SeriesLinesShare
unsafe { … } block bodies9,2382.5%
unsafe fn / unsafe impl bodies2,7080.7%
dual series — the honest total11,5573.2%

In the layered view, kernel/src carries 2,625 unsafe tokens, of which 1,174 sit outside the Framework layer (the service tier). 191 modules carry #![forbid(unsafe_code)] — compiler-enforced zero-unsafe, ratcheted by CI so the set only grows; 93 service files hold no unsafe at all. 69% of unsafe constructs carry a written // SAFETY: contract, and CI fails when a region appears in the tree without a ledger entry.

The defect history. 35 memory-corruption-class bugs over Rux's whole history, each adjudicated individually: 23 had the defect inside unsafe code or assembly, 12 were in safe code — and every one of those twelve is an ownership, refcount, lock-protocol or stack-depth decision (the reduction campaign contributed two: a manual refcount release kept beside an RAII handle, and a self-referential list head left pointing at a dead constructor temporary — both caught by the data-integrity battery, both fixed at the protocol level). The classes that dominate the CVE history of C kernels — indexing overrun, iterator invalidation, format-string injection, wild pointer arithmetic — are zero in safe code. Six of the 35 were caught in review before any boot ran them.

Formal verification. 164 Kani harnesses discharge the core unsafe code for all inputs; 1,184 host-side tests; loom enumerates the interleavings of the mutex, PI-chain and timer primitives; 4 SPIN models; Miri nightly.

"I am 90% safe Rust" is not the claim. The claim is: here is exactly what the remaining unsafe surface is, where it concentrates, and which tool watches it. That is auditable safety, not a slogan. See the security overview and the defect taxonomy.

The scheduler is a single global run queue (GRQ) with an explicit target: personal devices with 8–16 CPUs. The measured GRQ critical section is ≈60 ns and the buffer-cache hit rate is 99.1%. Performance gating is part of the merge flow — without measurement data nothing merges; performance is not a benchmark run afterwards, it is an admission condition for every change. §6What the 419,000 lines contain

  • Scheduler: the GRQ, sized for 8–16 CPU personal devices; critical section ≈60 ns; no load balancer, no task migration
  • Memory management: buddy page allocator with a magazine small-object allocator, a global page cache, per-task VMAs, reclaim
  • Filesystem: ext4 read/write, jbd2, an async batching block layer, a per-inode page cache and a lock-free dcache
  • IPC and binder: a complete binder (it carries OpenHarmony's whole service mesh), unix sockets, pipes, SysV IPC
  • Network: a self-written TCP/IP stack with socket-API semantics matched to the ABI
  • Drivers: virtio-blk (PCI and MMIO, async completion rings), serial, input devices; the display path renders both the GNOME desktop and the OpenHarmony launcher
  • Observability: a unified trace-event framework with tracefs (semantics aligned), a symbol table, debugfs, task dumps
  • Porting layer: x86_64 / riscv64 / aarch64; about 90% of the kernel is architecture-independent

Because the host can use KVM directly, x86_64 is the primary platform for both function and performance work, while riscv64 and aarch64 carry the build and regression gates. The in-kernel test suite is 1,584/1,584 green on riscv64, and the desktop session passes a 2,100 s zero-panic gate.

§7What is not finished

  • LTP: 1,139 of 1,869 pass; several hundred still fail. TIMEOUT cases are adjudicated one by one, and every failure that is not ours stays on record
  • lmbench: 13 rows trail, the largest at 22–26×; 1 MiB direct write sits at 0.75–0.83×. Each row carries a measured decomposition of the gap
  • The unsafe surface: 3.2% (11,557 lines) still depends on human review; the reduction target is ≤5,000 unsafe lines (≤1%) with a per-block irreducibility proof (docs/development/unsafe-5000-plan.md)
  • Kani covers the core unsafe code, not every key path; loom and SPIN cover the concurrency primitives
  • Whether the AI working model holds at 400,000 lines is under observation, not settled
  • The 29 registered divergences need their compatibility evidence kept current

All of this is stated on the site. Rux is not a finished product; it is an engineering effort in progress.

§8Closing

I am writing Rux first to test what AI-generated code can do, and second because I want one thing: the performance of a monolithic kernel, the Linux ABI as a binary contract, and Rust's auditable safety — all three at once. Progress so far looks good, and while I have the time I will keep updating it; the day it stops, it will be because I found a new hobby.

The code is on GitHub; start with Getting started, or go straight to the architecture.
