The unsafe audit ledger

The memory-safety TCB's definition, the consolidation rules, machine-census numbers and the roadmap — answering "how much unsafe exists, where, and under what constraints" · Canonical: docs/architecture/safety-and-performance.md (the consolidation round + the INV index), docs/architecture/kernel-layers.md (the layering rules)

§1Defining the memory-safety TCB

This kernel's memory-safety TCB (trusted computing base) is defined as: the code whose memory safety depends on human review rather than the Rust compiler — i.e. every line inside an unsafe region. Everything else is memory-safe by construction (compiler-enforced). The collection campaign completed 2026-11-27, and 2026-11-28 added per-statement narrowing + safe-function repatriation: those lines all live in 18 audited per-subsystem unsafe.rs files plus tests/, and the other ~401 files forbid unsafe at the compiler (machine gate green repo-wide, rc=0). The dual-series reading: unsafe totals 3,936 lines = 0.99% of 397,552 physical lines (kernel/src, tests/ excluded) — block series 1,329 blocks / 3,661 lines (0.92%), unsafe fn/unsafe impl series 165 items / 275 lines (0.07%); campaign arc: 22,881 lines = 5.76% post-collection (2026-11-27) → 3,936 lines = 0.99% (2026-11-28), with the pre-campaign register holding 6,396 unsafe regions.

The honest boundary (carried by every ledger report): Rust's unsafe discipline covers accidental memory unsafety only. It is not a proof against logic bugs, ABI/spec violations, or compromised build tooling — those are carried by formal verification, the defect taxonomy, and stress testing (the other pages of this section).

  • New unsafe has nowhere to go: writing unsafe in the forbidden set is a compile error, not a review comment; adding unsafe means entering the subsystem's audited file with an INV contract — TCB growth is constrained by the compiler and the gate, not by convention.
  • The user-memory boundary: the syscall entry validates and translates user pointers uniformly; the rest of the kernel does not touch user memory directly — user copies go through arch/uaccess_safe.rs's address/slice-typed copy_in/copy_out (INV-UACCESS-1: the kernel-side operand is proven by the type system, the user side is access_ok-checked with the exception table as the backstop).

Region basis (per-statement granularity)

Every unsafe region is per-statement granularity: a statement stays inside unsafe if and only if the compiler requires it (narrowing guided by E0133, landed 2026-11-28; zero behavior change — block boundaries have no codegen effect). The arch floor: arch/unsafe.rs carries 2,181 unsafe lines (of the file's 25,343 lines); 73 safe functions were repatriated from it to their home subsystem files.

Accounting note: the dual series (block-body lines + fn/impl-body lines) is the headline number; the individual statement is the audit-registration unit — both are machine-generated. External reference point: Asterinas (USENIX ATC'25, a same-class Rust kernel) reports a memory-safety TCB of ~14% (no dual-series figure published).

§4The forbid coverage and the roadmap

  • Current: 401 files carry #![forbid(unsafe_code)] and the machine gate (scripts/gate_unsafe_mainline.py) is green repo-wide (rc=0) — the campaign's target state (zero unsafe outside the audited files) is reached and machine-enforced.
  • The campaign's quantitative target (≤5,000 lines, ≤1%) is met: 3,936 lines = 0.99%; the audited floor stays under the double constraint of the machine gate and the compiler.
  • The graded audit continues: class 1 (checked accessor reads) → class 3 (raw pointers with hand-rolled invariants); every audited block's INV contract is registered in safety-and-performance.md's Primitive INV index.

§5The layering argument: why this shape deserves trust

  • Class elimination (compile time), against C-kernel CVE history: buffer overruns (bounds-checked slices), Arc-owned use-after-free/double-free, data races on typed shared state (Send/Sync), iterator invalidation (borrowck), format-string injection (typed formatting) — the dominant classes are unrepresentable in safe code; the taxonomy's zero pointer-expression defects is the empirical face of the same argument (see taxonomy).
  • The density argument: the arch floor file (arch/unsafe.rs, 2,181 of 25,343 lines) carries the inevitable concentration of three-arch hardware operations — the consolidation's living sample: unsafe area scales with primitive complexity, not API surface.
  • The pairing argument: every primitive carries (a) a Kani harness, (b) a proptest, and (c) a Verus function spec (the registered next step, page-flag/refcount algebra first); RustBelt is cited as the trust anchor, not a build dependency.
  • The budget argument: the monotone-down rule on the dual-series reading (campaign arc 5.76% → 0.99%) + unsafe in the forbidden set being a compile error — TCB growth is constrained by the compiler and the machine gate, not by convention.
