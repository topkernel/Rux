The layered unsafe ledger

The memory-safety TCB's definition, layering rules, per-directory budget and the shrink roadmap — answering "how much unsafe exists, where, and under what constraints" · Canonical: docs/architecture/kernel-layers.md, docs/development/tcb-ledger.md (script-generated)

§1Defining the memory-safety TCB

This kernel's memory-safety TCB (trusted computing base) is defined as: the code whose memory safety depends on human review rather than the Rust compiler — i.e. every line inside an unsafe block. Everything else is memory-safe by construction (compiler-enforced). The engineering goal is to give a monolithic kernel microkernel-adjacent safety through language-level isolation: shrink the unsafe TCB into a small privileged Framework layer.

The honest boundary (carried by every ledger report): Rust's unsafe discipline covers accidental memory unsafety only. It is not a proof against logic bugs, ABI/spec violations, or compromised build tooling — those are carried by formal verification, the defect taxonomy, and stress testing (the other pages of this section).

§2The layering rules

LayerContentsunsafe policy
Frameworkthe hardware/privilege TCB: trap entry, page tables, context switch, raw MMIO/DMA, uaccess, low-level sync primitives (arch/, mm/, interrupt/, the virtio·intc·timer·pci cores, console/printk/sbi/main etc.)unsafe permitted; every block carries a // SAFETY: invariant comment, coverage tracked in the ledger
serviceeverything userspace-facing (syscall, fs, ipc, net, process, the sched upper layer, cgroup, procfs...)#![forbid(unsafe_code)] is the target state (currently 179 modules compile-time forbidden; 93 service files already unsafe-free)
diagnosticsdfx/ forensic instruments, raw-memory toolingreported separately — diagnostic churn must not hide inside the Framework bucket
testtest codeexcluded from the headline figure
  • The classifier is longest-prefix match; unmatched paths default to service — new files start in the safest bucket and promotion is an explicit act.
  • The capsule boundary (the Tock pattern): the syscall entry validates and translates user pointers uniformly; the rest of the kernel does not touch user memory directly. syscall/io.rs going from 69 unsafe tokens to zero is a worked instance — user copies now go through arch/uaccess_safe.rs's address/slice-typed copy_in/copy_out (a new Framework module).

§4The forbid effort and the shrink roadmap

  • Session 1 (2026-10-29): 113 files carry #![forbid(unsafe_code)] (46 service); Session 2 (2026-10-31): the first named shrink target, syscall/io.rs — 69 tokens → 0.
  • Targets (recorded in security-design.md): forbid files 47 → 90, unsafe-bearing service files 123 → 60 (a two-quarter window).
  • SAFETY-comment coverage 64% → 95% (class 2-3 blocks) is the goal.
  • The graded-audit plan: class 1 (checked accessor reads) → class 3 (raw pointers with hand-rolled invariants); the ledger's headline will add "class-3 tokens in service code" — the number that actually predicts field bugs. The audit-coverage gate: scripts/review_coverage.py --check fails the build when the tree gains a file the map does not know about.

§5The layering argument: why this shape deserves trust

  • Class elimination (compile time), against C-kernel CVE history: buffer overruns (bounds-checked slices), Arc-owned use-after-free/double-free, data races on typed shared state (Send/Sync), iterator invalidation (borrowck), format-string injection (typed formatting) — the dominant classes are unrepresentable in safe code; the taxonomy's zero pointer-expression defects is the empirical face of the same argument (see taxonomy).
  • The density argument: sync at 2.8% unsafe density is the layering's living sample — unsafe area scales with primitive complexity, not API surface.
  • The pairing argument: every Framework primitive carries (a) a Kani harness, (b) a proptest, and (c) — as the Framework shrinks — a Verus function spec (the registered next step, page-flag/refcount algebra first); RustBelt is cited as the trust anchor, not a build dependency.
  • The budget argument: the monotone-down rule on the 3.6% dual series + every newly added unsafe requiring a commit-body explanation of "why safe code was not possible" — TCB growth is constrained by process, not convention.
