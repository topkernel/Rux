§3Test forms

  • In-kernel suite (make test): 73 test files across eight domains (memory / process / fs / ipc / signal / network / driver / syscall); all assertions run inside the QEMU guest (a kernel crate cannot host host-side #[cfg(test)]). The CI smoke gate (smoke.yml) runs the riscv64 leg on every push.
  • Integration cluster: multi-process unattended runs + probe matrix (integration-test-report.md); the GUI has a 23-check pixel/serial gate (test/ubuntu-gui/verify.py) with pixel-identical cross-boot comparison (convcheck).
  • Formal verification: 1104 proptests binding on every push; Kani (157 harnesses) / SPIN / Miri nightly (see the Security section).
  • 4,200+ test cases in the repository (suite + probes + benchmarks + proofs).

§4Method and adjudication discipline

  • Every number carries its rig: architecture, accelerator, kernel profile, host-load discipline — a number without a rig is not a result.
  • Append-only reports: a new run appends a section or refreshes the standing table with its date; history is never silently rewritten.
  • Flake isolation: new full-scan failures are isolated-rerun twice before being called regressions (known flake families: accept02, getrusage04, kill02, genfmod, rename/statfs).
  • NOT-OURS ledger: the same musl LTP binaries run on the host Linux kernel; failures that reproduce there are recorded as test/environment issues, not kernel gaps.
  • Instrument misdiagnoses are archived too: PTGUARD/FREEGUARD false positives (mapcount=−1 is a sentinel), the first PT_LEDGER double-free — negative results with receipts stay in the record.
