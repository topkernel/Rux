Rux 是什么

用 Rust 从零编写的 Linux ABI 兼容操作系统内核 · kernel/ 树 679 文件 / 419,958 行(其中 Rust 408,864 行)· 349 个系统调用 · LTP 1,139/1,869

§1为什么我要自己写一个内核

市面上的 Rust 内核,要么是教学玩具,要么是微内核原型,要么兼容性靠"syscall 覆盖数量"声称。我想要的东西很具体:宏内核的性能底盘、Linux ABI 的二进制契约、Rust 的可审计安全。三样都要,一样不能少。

于是有了 Rux。代码全部公开,这篇文章就是简单说明:我做了什么、怎么做的、代码长什么样、哪些地方我还没做完。

最初的动机很具体:我在 Ubuntu 上同时开十几个 agent 工作,打字延迟到一两秒,不可接受 —— 与其继续调别人的内核,不如自己写一个。这个动机决定了后面所有的取舍:调度器是单一全局运行队列(GRQ),面向 8–16 CPU 的个人设备做减法,在该范围内消除负载迁移和任务窃取;从设计开始就没有考虑服务器内核。

§2ABI 兼容:不说"支持多少 syscall",说"你直接启动试试"

我的设计原则一句话:ABI 是契约,内部实现自由。

对外,Linux 用户态能看到的一切都是契约 —— 系统调用号与语义、ELF/auxv、futex、POSIX 与 SysV IPC、binder、磁盘上的 ext4、procfs/sysfs/debugfs/tracefs 布局,连 glibc 动态加载器会去读的 uname 字符串都需要对齐(我也不想对齐,不对齐启动不了)。当前实现 349 个系统调用(asm-generic 表;x86_64 原生编号翻译到同一张表),LTP 全量扫描 1,869 项过 1,139 项。

对内,不受主流实现的历史包袱约束。每一项和主流实现不同的内部设计都记录在案、附带兼容性证据,当前登记 29 项设计分歧(设计分歧登记表)。

关键是验证方式:不拿一组精心挑选的 syscall 测试说自己兼容,我拿未修改的发行版镜像直接启动:

发行版启动结果环境
Ubuntu 22.04进入 GNOME Shell 交互桌面;整链 2,100 秒 smp4 零 panic 门禁通过riscv64
Ubuntu 24.04systemd 255 到达 multi-user 与 graphical 目标,支持串口登录x86_64 + KVM
OpenHarmony135+ 服务全部拉起,到交互式 launcher(bootanimation、hiview、binder 网、输入链路)x86_64 + KVM
不打补丁、不重编译、不改配置。syscall 覆盖率是数字,端到端启动是事实。

§3AI 编码不是噱头,是工程方法

这件事我知道会有争议,所以把话说清楚:Rux 的子系统 —— 调度器、内存管理、ext4、binder、网络栈、验证框架 —— 所有的代码、文档、主页全部由 AI 实现,人类负责目标设定、评审与合并。

具体模式:多代理并行开发,每个任务独立工作树、独立分支,主会话审阅合并;每日多轮合并,全量回归验证。当前约 200 个工作树在跑。合并有唯一门禁(AGENTS.md):三架构构建 + 全量内核套件 + 分层性能门禁 + 数据完整性检验,缺一项不合并。

这不是"用 Copilot 补几行代码"。这是把 AI 编码放到子系统完整实现的位置上,人类退到架构评审和合并门禁。这个模式能不能在 40 万行规模上长期成立,我自己也在验证。但至少现在,它产出了一个能在真实发行版上启动桌面的完整内核。

§4安全:不喊"Rust 所以安全",给你看明细

"Rust 所以安全"这句话大家听腻了。真正有价值的是:unsafe 里出过什么事,我怎么管的。

unsafe 面有多大。kernel/src 共 396,139 行,按仓库内的审计记录脚本口径:

口径行数占比
unsafe { … } 块体8,7592.2%
unsafe fn / unsafe impl 函数体2,5390.6%
双口径合计(诚实总数)10,7422.7%

分层口径下,kernel/src 带 2,625 个 unsafe 记号,其中 1,174 个在 Framework 层之外(service 层)。165 个模块带 #![forbid(unsafe_code)],由编译器强制零 unsafe、CI 单调性检查（属性集合只增不减，移除即构建失败）;93 个 service 文件已无 unsafe。69% 的 unsafe 构造带书写的 // SAFETY: 契约;树内出现审计记录未登记的区域,CI 直接失败。

缺陷史。Rux 全史 35 例内存破坏类缺陷逐一归档:23 例在 unsafe/汇编,12 例在 safe 代码 —— 而这 12 例全部是所有权/引用计数/锁协议/栈深决策类(缩减战役贡献 2 例:RAII 句柄旁保留的手动引用计数释放、指向已亡构造临时的自引用链表头;均由数据完整性电池捕获,均协议层修复);而 C 内核里最常见的指针越界、迭代器失效、格式串注入、野指针运算,在 safe 代码里是 零。另有 6 例在 boot 之前就被代码评审拦下。

形式验证。164 个 Kani harness 对核心 unsafe 代码做全输入证明;1,184 个宿主侧测试;loom 枚举互斥锁、PI 链与定时器的交错执行;4 个 SPIN 模型;Miri nightly。

不说"我 90% 是 Safe Rust"就完事 —— 我告诉你剩下 3.6% 里出过什么、集中在哪、有没有被工具盯住。这是可审计的安全,不是口号。详见 安全总览与缺陷分类学。

§5性能:同机同加速对照,领先的落后的都放出来

我用 QEMU + KVM 同机同加速对照,不拿不同环境的数据互相比。

测试类别Rux 相对 Linux
lmbench 27 项13 项领先:信号量 8.97×、上下文切换 5.1–6.3×、管道 5.84×、缺页 2.8×、页缓存文件读 1.45–1.54×;13 项落后或持平,最大差距 = 文件创建吞吐 22–26×,其次是回环 socket 延迟 2.1–2.2×

调度器是单一全局运行队列(GRQ),目标场景写得很明确:8–16 CPU 的个人设备,GRQ 临界区实测 ≈60 ns,buffer cache 命中率 99.1%。性能门禁进合并流程 —— 无测量数据不予合并,性能不是事后 benchmark,是每次变更的准入条件。各套件的完整表格与方法:性能总览。

§641 万行里有什么

  • 调度器:GRQ,面向 8–16 CPU 个人设备;临界区 ≈60 ns;无负载均衡、无任务迁移
  • 内存管理:buddy 页分配器 + magazine 小对象分配器、全局页缓存、每任务 VMA、回收
  • 文件系统:ext4 读写、jbd2、块层 bio 异步批量读、每 inode 页缓存与无锁 dcache
  • IPC 与 binder:完整 binder(支撑 OpenHarmony 全部服务互通)、unix socket、pipe、SysV IPC
  • 网络栈:自研 TCP/IP,socket API 语义对齐
  • 驱动:virtio-blk(PCI/MMIO 双模、异步完成环)、串口、输入设备;显示路径支撑 GNOME 与 OH 渲染
  • 可观测性:统一 trace-event 框架 + tracefs(语义对齐)、符号表、debugfs、任务转储
  • 架构移植层:x86_64 / riscv64 / aarch64,约 90% 内核代码架构无关

因为 host 可以直接用 KVM,x86_64 是功能与性能主战场,riscv64 和 aarch64 承担构建与回归门禁;内核自带测试套件在 riscv64 上 1,584/1,584 全绿,桌面会话通过 2,100 秒零 panic 门禁。

§7我还没做完的事

  • LTP 1,869 项过 1,139 项,还有几百项没过;TIMEOUT 类按 P0 规则逐行归因,非本内核造成的失败逐条留档
  • lmbench 13 项落后,最大 22–26×;1M 直写 0.75–0.83×。每行都带测得的差距分解
  • unsafe 面还有 2.7%(10,742 行)依赖人工评审;收缩目标是 ≤5,000 行(≤1%),每块残余都要写明不可约理由(审计记录与阶梯见 docs/development/unsafe-5000-plan.md)
  • Kani 覆盖核心 unsafe,还没铺到全部关键路径;loom 与 SPIN 覆盖并发原语
  • AI 编码模式能不能长期撑住 40 万行,我自己也在观察
  • 29 项设计分歧的兼容性证据需要持续维护

这些我都在官网上说明了。Rux 不是完成品,是一个正在推进的工程。

§8最后

我写 Rux,首先是想测试 AI 生成代码的能力,另外就是我想要一个东西:宏内核的性能,Linux ABI 的二进制契约,Rust 的可审计安全,三样同时成立。目前来看进展可喜,因为现在赋闲在家,所以有时间的话会一直更新下去,哪天不更新了,可能就是找到了新的爱好了。

代码在 GitHub,开始动手看 快速入门,或者直接看架构设计。
