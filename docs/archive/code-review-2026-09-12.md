## 1. Top 15 highest-priority issues (cross-subsystem ordering)

1. **[ARCH-C1] uaccess.S exception table systematically misplaced by one instruction** (`arch/riscv64/uaccess.S:142-347`)
   The `EXTABLE` macro defines the label **after** the instruction, so the label binds to the next instruction. None of the real faulting memory-access instructions in `__copy_from_user`/`__clear_user` are covered by the exception table, and `fixup_exception()`'s exact match always misses → any user pointer that is "within the legal range but unmapped" (including NULL, since USER_START=0) passed to read/execve/strncpy_from_user etc. triggers a kernel-mode page fault → KernelPanic → wfi dead loop or a permanent fault loop. **A single bad user pointer hangs the whole machine in one step.** Verified against the binary via readelf/objdump; `__copy_to_user` "accidentally" works (its store happens to be covered), masking the problem. Fix: move EXTABLE before the covered instruction (Linux-style backward reference), and add a validation script checking one-to-one correspondence between table entries and memory-access instructions.

2. **[ARCH-C2] trap.S entry clobbers t0/t1/t2 before saving them** (`trap.S:210-212, 232-252, 491-510`)
   The common dispatch path, user path, and kernel path all use t0-t2 for stack selection/address determination before saving the GPRs, and only then execute `sd x5/x6/x7` — storing garbage. Timer interrupts randomly corrupt the temporary registers of user programs and kernel Rust code (LLVM uses t0-t2 heavily) hundreds of times per second. **This is very likely the root cause of the recurring "probabilistic" crashes in commit history.** Verified against the binary (PT_T0=0x1FFFF etc.). Fix: following Linux, immediately upon entry save all GPRs using only `sd xN, PT_xN(sp)`, and move the stack-selection logic after the saves.

3. **[VFS-C1] open()/path traversal have zero DAC permission checks** (`fs/vfs.rs:1111-1199, 347-489`)
   `file_open()` never checks MAY_READ/MAY_WRITE; `path_lookup()` never checks MAY_EXEC (the search bit) when traversing directory components; the whole kernel calls `generic_permission` in only 3 places (parent-directory write, truncate, faccessat), and `Inode::op_permission` has zero callers. **Any unprivileged user can `open("/etc/shadow", O_RDWR)`**; write() on an fd opened O_RDONLY also succeeds. The fix points are concentrated: path_lookup per directory component + file_open by O_ACCMODE + read/write by f_mode.

4. **[SYSA-C1] The read/write family heap-allocates directly on user-controlled count** (`syscall/io.rs:83,145,250,774`, `syscall/file.rs:281-285`)
   `vec![0u8; count]` with count up to 256GB (access_ok only checks the range) → allocation failure → `alloc_error_handler` panic. A single `read(0, buf, 0x4000_0000)` kills the whole machine. Linux clamps to MAX_RW_COUNT (2GB). The io_uring path has the same disease (`io_uring/mod.rs:587,621`).

5. **[PROC-C1] Malicious ELF p_offset/p_filesz have no bounds validation → kernel panic** (`process/exec.rs:177`)
   `&program_data[offset..offset+file_size]` slices directly, with segment-header fields coming from a user-controlled file. Same disease: the interpreter's (PT_INTERP) e_phoff is also unvalidated (`fs/elf.rs:405-411`, reachable kernel memory disclosure/OOB read); the init path `init.rs:267` likewise. Linux returns ENOEXEC and never panics.

6. **[NET-C1/C2] The network stack has never actually worked in either the RX or TX direction**
   - RX: `ethernet_rcv()` never calls `eth_pull_header()` (defined at ethernet.rs:123, zero calls repo-wide) — all inbound packets enter ip_rcv/arp_rcv still carrying the 14-byte Ethernet header and are silently dropped after being parsed at the wrong offset.
   - TX: `SkBuff::alloc` headroom is only 16 bytes (buffer.rs:149); TCP/IP/ETH need 54 — every `skb_push` of a TCP segment or ICMP reply necessarily fails, **only ARP can be transmitted**; each failure also leaks ~1.5KB of skb (SkBuff has no Drop).
   - Related: ethertype write missing to_be() (H1), TCP/UDP checksum pseudo-header read inconsistencies (H2/H3), handshake ISN not byte-order converted (H4). The previous rounds' "FIXED" claims were never verified with real RX/TX (unit tests only tested constants).

7. **[NET-C3] The syscall layer uses process fds to directly index the global socket table** (`net/socket.rs:572` + 12 places in `syscall/network.rs`)
   `get_socket(fd)` treats the process fd as a global slot number; stdio occupies 0-2, so the first socket has fd=3 while its slot=0 → listen/connect/accept/sendto/recvmsg etc. — **the vast majority of socket syscalls get EBADF or operate on another process's socket**. Only bind goes through `get_socket_from_fd` (the correct exemplar).

8. **[EXT4-C2/C3/C4] Routine ext4 operations silently corrupt the file system**
   - truncate frees extent physical blocks but does not delete/shrink the extent entries (mod.rs:1457-1485) → after truncation, extending writes touch **blocks that were freed and possibly reallocated to other files** (cross-file data corruption, without any error).
   - Fast-symlink unlink frees the target string's bytes as a block number (namei.rs:1553-1558) — `ln -s sh x; rm x` frees a live block.
   - Writing a hole into an extent file directly overwrites the extent header with direct block pointers (file.rs:250-281) — after ftruncate extends, a write destroys the extent header.
   - Also: the extent tree has no recursion depth limit/buffer bounds validation (C1, malicious image OOB read + stack overflow); images with fs block size ≠4096 read/write misaligned and destroy the disk (H1); superblock geometry has zero validation with multiple division-by-zero panics (H2).

9. **[SYSA-C2] mremap loses all old data after moving** (`syscall/memory.rs:707-739` + `mm_ops.rs:82-96`)
   The new mapping is lazy (only the VMA is created, no pages mapped), and `copy_old_to_new_pages` requires the new address to already have a PTE → not a single page gets copied before munmap of the old region → the first access to the new region faults in the **zero page**. glibc/musl realloc goes through this path — silent memory corruption.

10. **[DRIV-C1/C2] MMIO virtio device queue programming is wrong across the board**
    - virtio-blk MMIO: PCI common-config offsets (0x20/0x28/0x30/0x1c) are written into the MMIO register space, QueueReady(0x44) is never set, yet init returns Ok (virtio/mod.rs:232-268) → an MMIO-only configuration cannot mount the root file system.
    - virtio-net MMIO: avail/used ring addresses explicitly written as 0, desc pointing at a dead table (virtio_net.rs:187-257) → RX/TX completely non-functional, and each transmit spins for seconds with interrupts off while holding a lock, then **falsely reports success**.
    - PCI path: feature negotiation accepts EVENT_IDX wholesale while used_event is heap garbage (H2, the root cause of the "random timeout" 5-retry patch); INTX IRQ number off by one (H3); async reads missing F_WRITE always return EIO (H4).

11. **[IOU-C1] io_uring_enter/register do not validate fd type → type confusion, arbitrary kernel read/write** (`io_uring/mod.rs:852-893`)
    The private_data of pipe/eventfd/mem files is directly coerced to IoUring, and pointers inside the fake ring are read/written via read/write_volatile — a single line yields arbitrary kernel read/write or an instant crash. A missed surface of the F15-03 fix (close validates ops); the mmap path has the check, enter/register do not. Related: enter/close concurrent UAF (H1), ring physical pages never freed (H2).

12. **[PROC-P02] vfork double lost-wakeup race (newly introduced by commit fddcac2)** (`process/fork.rs:381-397`)
    The child calls `enqueue_task` before registering `vfork_parent`; and the parent sets state UNINTERRUPTIBLE before schedule without re-checking. Under SMP, if the child execs first → the wakeup is lost → the parent **sleeps forever UNINTERRUPTIBLE** and the process tree hangs. musl posix_spawn uses vfork by default. Linux is immune via completion.

13. **[IPC-C3/C1] futex/sem core waiting primitives are broken across the board**
    - `FUTEX_WAKE/REQUEUE` with more than 8 waiters silently unlinks them without waking (futex.rs:158-212) — `pthread_cond_broadcast` with >8 waiters permanently hangs threads in batches.
    - semop blocking semantics completely inverted (sysv_sem.rs:686-697): a normal blocking P returns EINVAL, while IPC_NOWAIT blocks forever — the SysV semaphore wait path is completely unusable.
    - Timeouts never take effect: semtimedop/mq_timed*/futex(timeout) all have no armed timer, so every wait with a timeout hangs forever (H3).
    - futex waiter pool concurrent double allocation (C2), slot UAF after wakeup (H4).

14. **[MM-C3] swap-out of shared pages frees swap slots still referenced** (`mm/vmscan.rs:263-286`)
    After a fork, a COW page (refcount=2) is swapped out, the slot is freed but both PTEs still hold the entry → after slot reuse, a page fault reads **another page's data** (silent cross-contamination) + physical page leak. Related: the compaction path dereferences raw physical addresses and necessarily panics (C1, page_desc.rs:547), after migration the PTE cannot be reinstalled and the data becomes the zero page (C2), munmap only clears PTEs without put_page (page leak, arch H3 / mm H4 same origin), fork does not copy swap entries and wrongly COWs SHM pages (mm H5).

15. **[DOCS] The documentation system is widely out of sync with the code**
    - `docs/architecture/kernel-lock.md` describes the **already completely removed Kernel Big Lock** as the current mechanism throughout (zero references in code, no amoswap in trap.S); riscv64.md/roadmap.md have the same disease.
    - README/structure/unit-test-report numbers contradict each other in four places (348 syscalls actually 344; 825 cases vs 901 PASS+94 SKIP vs static 1451 assertion points; the 3,777 total is arithmetically inconsistent; four versions of the line count).
    - CLAUDE.md (the AI collaboration entry point) has 3 broken links + Phase 36 (now 52) + "203 test cases".
    - getting-started's mini-ltp/RELEASE=1/distclean//bin/shell are all irreproducible; the debugging guide's persistent-log description contradicts commented-out code.
    - The LTL properties verified by SPIN were never all verified (Makefile does not pass -N; 8 claimed but ~3 actually checked); the 825 kernel unit tests have no CI and no automatic verdict; whole files of always-true fake tests exist (tcp_handshake.rs, mem_cow.rs, smp.rs).

## 2. Arch / Boot (kernel/src/arch/riscv64/ + sbi.rs, 22 items)

### Critical
- **ARCH-C1** exception table misplacement (see Top 1). `uaccess.S:142-347`, `exception.rs:88-93` exact match.
- **ARCH-C2** trap entry clobbers then saves t0/t1/t2 (see Top 2). `trap.S:210-212, 232-252, 491-510`.

### High
- **ARCH-H1** FPU saved but never restored: `context.rs:263-307` saves f0-f31 on switch-out, the switch-in side never restores (zero callers repo-wide), and the FP first-use trap does not reload either → cross-task floating-point corruption + information disclosure. Linux does `fstate_save(prev)` followed by unconditional `fstate_restore(next)`.
- **ARCH-H2** vfork lost wakeup (same as PROC-P02).
- **ARCH-H3** munmap/MAP_FIXED only clear PTEs without put_page (same as MM-H4): every unmap leaks physical pages; musl large malloc/dlclose exhausts memory over long runs.
- **ARCH-H4** do_exit synchronously frees the root page table while still running on it (`exit.rs:110-124`): any non-global mapping TLB miss in the free-switch window walks a reclaimed page table → guaranteed to explode on real SMP (currently masked by tcg single-thread). Linux defers via active_mm/mmdrop.

### Medium
- **ARCH-M1** Kernel-mode illegal instruction/unknown exception silently skips 4 bytes (`trap.rs:215-221`) — masks kernel bugs; `print_cpu_info` reads M-mode CSRs from S-mode every time and gets skipped, so the boot log prints garbage HART IDs.
- **ARCH-M2** A nested trap landing on the per-CPU interrupt stack overwrites the outer pt_regs (`trap.S:236-268`; the early path checks this, the normal path does not).
- **ARCH-M3** munmap does not support VMA splitting and cross-VMA ranges only remove the first one (`mm_ops.rs:374-409`) → already-munmapped memory gets "resurrected" by page faults as the zero page (same as SYSA-H1).
- **ARCH-M4** Stack growth lacks the "near SP" check (`page_fault.rs:69-109`) → out-of-bounds deep writes silently grow the stack instead of raising SIGSEGV (Linux checks address >= sp-65536).
- **ARCH-M5** fork COW downgrade does only a local sfence (`mm_ops.rs:1084`) → other CPUs retain writable TLB entries and keep writing COW pages, silently corrupting without needing a page-fault race (an independent consequence of the known PTL limitation; a simple mitigation exists: broadcast TLB invalidation).
- **ARCH-M6** ecall instruction-length determination wrong + reading user instructions without SUM (`trap.rs:348-373`): c.ecall at 4-aligned addresses gets skipped by 4 bytes; when epc%4!=0 a raw read of a user address occurs → combined with C1 this likewise hangs the machine.

### Low (summary)
- L1 `strncpy_from_user` returns EFAULT for empty strings (execve("") should be ENOENT); L2 `send_ipi` ignores SBI failures; L3 arch heap-allocating `copy_thread` dead code conflicts with the current fork semantics; L4 `map_region` underflows on unaligned start; L5 KERNEL_STACK_SIZE hardcoded in three places; L6 the LR clear `sc.d x0,t2,(t2)` writes the address value instead of 0; L7 file page faults piggyback on f_pos (CLONE_FILES race); L8 brk shrink does not unmap; L9 `Perm::None` generates the R bit; L10 `.ex_table` only ALIGN(4).
- Info: the entire ASID infrastructure is unused (switch_mm always ASID=0 + full sfence, correct but slow); the kernel linear mapping is RWX with no W^X; `map_page` does a full sfence per page.

## 3. Memory management (kernel/src/mm/, 30 items)

### Critical
- **MM-C1** `page_desc.rs:547` `copy_page_contents` dereferences a raw physical address (misses phys_to_virt) → the moment compaction actually runs, a kernel page fault panics.
- **MM-C2** `compact.rs:293-424` after migration `remap_page` gates on walking to a valid PTE, but unmap already zeroed the PTE → the new PTE can never be reinstalled, user data is silently replaced with the zero page + dst page leak.
- **MM-C3** `vmscan.rs:263-286` swap-out of shared pages frees still-referenced swap slots (see Top 14) + physical page leak.

### High
- **MM-H1** `vma.rs:346-351` VMA merging ignores file_fd/offset → adjacent mmaps of different files get merged, and the former file's range reads pages via the latter file's fd/offset (reads wrong data). Linux vma_merge requires vm_file/vm_pgoff to match.
- **MM-H2** `page_alloc.rs:52-69,164-177` + `zone.rs:455-577` buddy page-descriptor state transitions happen outside the zone lock (a 512-atomic-write window on the alloc side / modify-before-lock on the free side) → SMP free-list corruption, nr_free underflow, double ownership. Linux completes the whole block under the lock.
- **MM-H3** `vmscan.rs:180-291` the whole reclaim path has no page lock and no refcount pin → races with page faults/exit/free (after PFN reuse, writing someone else's page into swap).
- **MM-H4** (cross arch) munmap without put_page (same as ARCH-H3).
- **MM-H5** (cross arch) fork does not copy swap entries (the child gets the zero page when accessing a swapped-out page); MAP_SHARED/SysV shm writable pages get wrongly COW-downgraded → shared memory semantics broken after fork.
- **MM-H6** (cross arch) fork's VMA snapshot loses the offset → the child's file mapping reads pages at the wrong offset.
- **MM-H7** (cross syscall) mprotect's PTE rebuild drops the COW bit and PROT_WRITE directly sets W → bypasses COW, two processes write the same physical page.

### Medium (summary)
- M1 expand_downwards overlap-check range wrong → a same-key insert silently replaces a VMA; M2 kswapd lost wakeup (between the watermark check and set_state) → sleeps through pressure until OOM; M3 anonymous page-fault pages don't set SwapBacked and don't enter the LRU → vmscan skips all ordinary anonymous pages → no reclaim even with swap → kswapd fails 16 times in a row and goes straight to OOM kill; M4 the reclaim scan is O(all memory) with no cursor; M5 (cross) process exit does not clean swap entries (slots leak forever); M6 the swap area at the disk tail is not checked for FS occupancy [image layout to be verified]; M7 `main.rs:388` init_from_memblock argument error (an address passed as the size) + heap_size dual source; M8 allocation failure has no direct reclaim (try_to_free_pages dead code, the page-fault path goes straight to OOM); M9 swap type encoding bits overlap the COW software bit; M10 first_online_node_mut &mut aliasing UB; M11 fork COW mid-way OOM with no rollback; M12 memblock add double-counts overlaps in the superset case.
### Low: L1-L8 (mm_users_dec comment contradicts behavior, meminfo always 0, vmemmap half-initialized retry falsely succeeds, swap_free_slot double-free underflow, page-descriptor Reserved annotation missing, the documentation's refcount+2 outdated, PhysAddr::ceil overflow, rmap index 0 sentinel).

## 4. Process management + scheduling (35 items)

### Critical
- **PROC-P01** Malicious ELF p_offset/p_filesz unvalidated → panic (see Top 5).
- **PROC-P02** vfork double race → the parent permanently in D state (see Top 12; introduced by commit fddcac2).
- **PROC-P03** do_exit completely lacks orphan reparenting: the repo has no forget_original_parent equivalent. The parent exits before the child → surviving children's parent pointers dangle (ppid()/for_each_child dereference wild pointers, UAF) + orphan zombies leak forever (chronic PID-space exhaustion). Linux reparents to init.
- **PROC-P04** regression introduced by commit 994b306: deferred exit notify reads the wrong per-CPU slot (`sched.rs:746-763`) — `prev_cpu` is actually the CPU the awakened task was switched out of long ago (W), not the CPU the exiting task actually ran on (X) → SIGCHLD/parent wakeup can be **delayed indefinitely** (while a CPU-bound task holds the CPU, do_wait sleeps forever, the shell hangs). The old implementation (reading cpu_id() after the switch) was actually correct. Fix: use the existing per-CPU prev record in context.rs to fetch the exiting task's parent pid, eliminating the CPU inference.

### High
- **P05** AT_RANDOM points at AT_NULL (16 bytes of all 0) and rand overwrites the first 16 bytes of the AT_PHDR table (`exec.rs:395-542` slot arithmetic off-by-2): the stack canary is always 0 (the F05-11 fix is completely ineffective), and dynamic linking crashes when PT_INTERP comes first.
- **P06** RT priority semantics reversed from Linux (`rt.rs:19` trailing_zeros, smaller value wins) + no range validation: `chrt -f 99` is the lowest priority within the RT class; FIFO priority=0 doesn't return EINVAL but instead becomes the highest.
- **P07** sched_setscheduler changes policy without run-queue migration: a task can hang on two class queues simultaneously (two CPUs pick the same Task → structural disaster) or never get scheduled (FIFO→NORMAL stuck on the RT list, hung).
- **P08** RT task exit causes rt_nr_running underflow (`rt.rs:174-216` no on_rq guard) → the RT queue is permanently "non-empty", the idle fast path broken.
- **P09** CFS's globally unique `cfs_rq.curr` mis-accounts on 4 cores: update_curr updates "the task picked last" while the actually running task's vruntime stops growing → fairness completely distorted, tasks can starve.
- **P10** setpriority missing can_nice: an ordinary user can lower their own nice to -20.
- **P11** The setuid exec security chain is broken (`exec.rs:519` AT_SECURE always 0 + LD_PRELOAD not scrubbed + dropping from root uid doesn't clear caps) — a dynamically linked setuid-root program can be hijacked for privilege escalation via LD_PRELOAD. Companion **syscall-b C-02**: execve commits setuid credentials before loading succeeds; constructing a "semi-legal" setuid ELF whose load fails midway yields a root-credentialed old-image process (local privilege escalation).

### Medium (summary, 17 items)
P12 wake_up non-atomic (double wakeup inflates nr_running, DL double insert); P13 do_waitid misses 994b306's zombie re-check (same-family race); P14 wait4's pid==0/pid<-pgid semantics unimplemented (reaps the wrong process); P15 execve clears the signal block mask (POSIX violation); P16 DL gets wrongly throttled on its first tick (exec_start uninitialized); P17 DL refills the budget on every enqueue (CBS bandwidth control ineffective); P18 do_clone failure path leaks PID + pid_hash retains a wild pointer; P19 fork doesn't inherit nice/policy/affinity/comm (comm uninitialized, ps shows garbage); P20 sched_setaffinity validates then discards (returns success but has no effect); P21 kill group broadcast has no permission check (same as syscall-b H-01) + sleeping group members don't receive it; P22 kernel-thread exit becomes an unowned ZOMBIE (Task/PID leak); P23 new_task_at misses initializing comm/kernel_stack_bottom/ti_a0-2; P24 release_task doesn't run Drop (exe_path Box and pending SigQueue leak per process); P25 idle marking races with enqueue (wakeup delayed up to one tick); P26 execve doesn't check the x permission bit; P27 prlimit64/setrlimit succeed but don't persist (ulimit -n has no effect); P28 setgroups(0,NULL) doesn't clear the supplementary groups.
### Low: P29-P35 (rr_get_interval doesn't validate the policy, PRIO_PGRP/USER unimplemented, setpgid semantics missing, argv/envp silently truncated, wakeup vruntime clamp without tolerance, exit_group only exits the current thread, CLONE_VM mm_users only incremented never decremented).

## 6. Syscall layer — process/signal/network/time/misc (52 items)

### Critical
- **C-01** `sys_riscv_hwprobe` reads M-mode CSRs from S-mode (mvendorid/marchid/mimpid, `process.rs:2526-2540`) → illegal instruction → kernel dead-loop hang. glibc ≥2.38 calls it at startup. One syscall hangs the whole machine.

### 16.6 New finding NEW2 (added 2026-09-13, Critical): fork-child ext4 file operations trigger an SMP race

An **existing defect** located while chasing "all mrsh redirection/pipe subcommands dying (129/127, files 0 bytes)" (also reproduces on the cf6defc kernel):

### 18.1 NEW2 root cause convicted (dedicated agent, full code evidence)

**Mechanism 1 (root cause, Critical): a RUNNING task can be picked globally before its context is saved — two cores run the same task + a stale kernel stack**. `__schedule` (sched.rs:711-767) re-inserts prev into the global tree and **unlocks the GRQ before context_switch**; while prev's sp/ra are only saved in `__switch_to` (the sd ra/sp at context.rs:83-84).
