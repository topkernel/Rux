- ROOT CAUSE of "getcwd() failed: Success" (kernel ABI bug, FIXED in
  a2278150): sys_getcwd returned the buffer POINTER; the ABI is to
  return the path LENGTH. glibc's __getcwd keeps the raw syscall
  result in an `int retval` and treats it as a length: our pointer
  (0x2aaaa_xxxx0000-class heap/PIE addresses, bit 31 of the low word
  set) truncated to a negative int made glibc classify the successful
  call as an unclassifiable failure and return NULL with errno left
  at 0. dash then printed "Success" and crashed on the NULL cwd (the
  epc=0x2aaaaae2b6 addr=0x8 family). Fix: return cwd_len+1.
- runs/gnome-r3fix (FIXED kernel): getcwd failures 192 -> 0. But the
  session COLLAPSED into the "Oh no" error screen (lit @1260s,
  #e0e0c0): gsd-usb-protection SEGV-looped 33x (NULL GError deref on
  its "Failed to connect to screensaver service" warning path — gsd
  42.9 assumes error != NULL), and the respawn load blew 84 gsd
  register deadlines. Interpretation: with getcwd broken the helpers
  died instantly (cheap); fixed, they do real work, so the load the
  crash loop generates is no longer masked. Fix order matters: kill
  the crash loop (image-side, e5be15c1: UsbProtection dropped from
  RequiredComponents + Hidden=true; no UPower/usbguard on the image
  anyway), then the deadlines should be met like baseline.
- The dash-family SEGV epc=0x2aaaaae2b6 was NEVER dash: PIE base is
  constant 0x2aaaaaa000 (no ASLR observed for [exe]), and 0xe2b6 in

- PREEMPT-LEAK pid=0 pc=0x10000 rip=wfi: DEMOTED to reporter artifact

## Session 7 (2026-10-26 early, leg-5 after the 23:23 quota death)

- r8final RESULT (from preserved serials; leg-4 died before appending):
  KERNEL_PANIC @515s — "PANIC: index out of bounds: the len is 16 but
  the index is 16" at kernel/src/mm/small_alloc.rs:445, mid gsd-storm.
  M2 @441s, M3/M4 never reached. So the gsd-power drop did NOT get its
  validation on leg-4's kernel.
- Root cause (fixed in 65f35f47): the small-object allocator's
  per-CPU magazine row was found with len == 17 (MAG_DEPTH is 16). Two
  racing pushes that both passed the len<16 check at len==15 — possible
  only when two CPUs transiently resolve cpu_id() to the same row
  (tp->ti_cpu divergence window; the scheduler R55/R74 hunt family —
  every in-tree steer is gated but residual windows remain) or a wild
  write into the row. The next free-path drain then read buf[16], one
  past the row, and killed the kernel. Fix is allocator-local defense
  in depth: alloc pops only when 0 < len <= MAG_DEPTH; the free-path
  drain is bounded on both sides (indices >= MAG_DEPTH were never
  written by any push, so dropping them is safe; flush_batch
  re-validates every surviving entry against the page header); a len
  beyond 2x depth is dropped wholesale so a wild-written len can never
  stall a CPU under IF=0; every heal bumps MAG_ALIAS_EVENTS (printed
  as mag-alias-heals in the census line) + BAD_PAGE taint, so the
  scheduler/wild-write hunt lanes get a named counter instead of a
  dead desktop. No row atomics by design — that would mask the
  producer.

### INPUT -> SCREEN: root cause found and FIXED (kernel-side)
- r13live evidence: INPTRC=0 for the whole live session (1500s) while
  the desktop rendered; INPPL fired exactly 8x, all during Xorg's
  device-add; Xorg's InputThread EPSCAN'd exactly TWICE then slept
  forever. Timeout-loop readers get events (each expiry re-dispatches
  evdev_file_poll, which drains); an infinite-timeout waiter never
  does. Xorg's input thread is exactly that waiter (epoll_wait, no
  timeout, registered on the evdev poll_waitq by the P3 wait path).
- Mechanism: the event flow was pull-only — events move off the
  virtqueues ONLY inside evdev read/poll dispatches; push_event (the
  poll_waitq's only waker) runs at drain time; nobody drains because
  the only poller is asleep. Deadlock by design, exposed when P3
  (95796982, 2026-10-13) made epoll_wait sleep on producer wakes.
- FIX (99f0ef49, merged to main as 6ae8c8fb by the coordinator):
  IRQ-driven delivery — riscv64 gpex shared-INTx handler (ISR read =
  device-side EOI) + x86_64 shared INTx dispatch, deferring to an
  input tasklet BH that drains both queues with a collect-under-lock /
  deliver-outside split (INV-LOCK-6, block_bh_handler shape); INPUT_*
  guards in the evdev read/poll drain are now lock_irqsave; IRQ
  registration moved to the end of init_virtio_input. Gates: dual-arch
  rc=0, rv smoke 0 panics, suite 1112/1112 (controlled boot; the
  duplicate official make-test run was killed after the same binary
  passed — see maketest-fix2 notes re the image-lock collision).

### The no-light fork: root cause (mission 1) — VERDICT DELIVERED
- Census separation is total. Every no-light boot (r16/r17/r20/r22)
  carries 193-515 PREEMPT-HEAL firings (was=0x10001: leaked base
  preempt bit 1 under the tick offset, held and re-leaked across every
  10 s heal); every lit boot carries 0 (r19: 1 paint-class print).
  The heal census alone separates the classes 4-vs-4.
- Mechanism (r20, fully legible in the serial): during shell init a
  thread-group member exits and parks DEAD on its leader's
  dead_threads list, but its ownership qword {on_cpu=1, claim=X} is
  never released — the R85 lost-release terminal microstate, this
  time on the EXIT side. The reaper entering free_dead_member
  (exit.rs) spins `while member.on_cpu()` FOREVER (FDM-WAIT
  sweeper=538 member=677; r16: sweeper=535; both CPUs wedged in r20:
  sweepers 538+544, 233 heals EACH). The pick-side R85 heal cannot
  reach the member (it is unlinked; pick scans see linked tasks
  only). With SMP=2 the two wedged sweepers starve the box: shell
  wakeups WAKE-STRANDED behind them (pid=363 h1=(538/2610ms/pc=1),
  strands 1-38 s), shell init never completes, xwininfo shows the
  gnome-shell windows stuck 1x1, screen dark for the whole 2700 s.
  Kernel stays panic-free and input delivery stays 1:1 into the dead
  screen — every prior observation of the class falls out of this one
  wedge.
- Subclass split of the 4 dark boots: r16/r20 = the FDM lost-release
  spin (fix below covers these). r17 = same census class but a
  different un-sleepable loop (heal pid 482; NOT a sweeper — all its
  FDM sweeps cleared; likely the do_wait/finish_wait family pa73
  triaged; needs a taskdump capture to name). r22 = userspace heap
  corruption ("malloc(): corrupted top size") aborting gnome-session
  st=6 after 82 s, then the fallback path (gnome-shell --replace)
  and runit itself wedge (pid=1 + 0x1cd heals) — a distinct subclass,
  not kernel-scheduling.
- FIX (commit a384048c, R86): the exit-side twin of the R85 pick-side
  adjudication. free_dead_member's wait is bounded at 300 jiffies
  (3 s, ~1000x the legitimate TCG switch-out window); past the
  deadline member_release_stale_ownership (sched.rs) adjudicates
  under the GRQ — a DEAD, unlinked member named by NO CPU slot and NO
  in-flight SWITCHING_OUT executes nowhere and nothing will ever
  release its marks — and releases them with the exact store the
  switch protocol would have made (idempotent), with a capped
  FDM-STALE-RELEASE report carrying the R85 context tail. A live
  owner re-arms the deadline: legitimate windows behave exactly as
  before. GRQ-held read is required and sufficient: the slot flip and
  SWITCHING_OUT publish share one GRQ hold, so the reader can never
  free a task whose switch-out is still writing its saved context.
- Gate for the fix: dual-arch build rc=0 (riscv64+x86_64); minimal-
