## Task 4 — 1-of-9 boot flake: NOT REPRODUCED on current main

- fix2.log (aa64-fork lane, older kernel) signature: after init spawn,
  el1_sync data abort: far=0xffffc00080000020, sp=0xffffc0007fffff80,
  esr=0x96000005, CPU 1, PID 1 (sh).
- The faulting access is [sp,#0xa0] = S_X20 (PT_REGS_SIZE=0x140):
  `ldr x20, [sp, #S_X20]` in restore_and_eret with sp 0xC0 ABOVE the
  correct outermost frame base (stack_top - 0x140) — i.e., the exit
  path ran anchored to a frame 0xC0 too high, and the stack top sat at
  the linear-map end (last RAM page) so the over-range slot faulted.
  NOT a linear-map-size problem: the same sp error mid-stack would be
  silent.
- Boot-loop on THIS tree (main@40e925fd + teardown + PL011 commits):
  round 1 = 12/12 clean (run/flakeloop/summary-1.txt, boot-N.log),
  round 2 = 12/12 clean (summary-2.txt). 0 flakes in 24.
- Candidate fixes already on main between fix2.log's kernel and now:
  per-arch WAKE_PTR_FLOOR (wakeup drops hit every aarch64 heap Task),
  aarch64 context-switch repair series (R56-heal), exec TLS flush.
- kstack bookkeeping audited: alloc_kernel_stack records bottom,
  top = bottom + 0x20000 (config KERNEL_STACK_SIZE); trap.S re-anchor
  uses the same constants — no static mismatch found.

  crash PASS (getpid01 children TPASS x15). mmap is NOT the cause
