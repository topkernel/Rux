## The code defect

kernel/src/arch/riscv64/mm/mm_ops.rs handle_cow_fault (identical twin
in kernel/src/arch/x86_64/mm/mm_ops.rs:2189):

    let _pte_guard = pte_lock_for(mm).lock_irqsave();   // IRQs off + epoch
    ... re-checks, fast path ...
    let new_phys = match alloc_user_phys_page() { ... }  // FULL slowpath
                                                              INSIDE

The whole GFP_USER slowpath — reclaim retry, OOM-kill wait,
free-list churn under fragmentation — runs with (a) the local hart's
IRQs disabled (lock_irqsave) and (b) the PTE epoch read-held, so:

- every global PTE writer on the other hart starves (hart0's spin),
- every same-mm PTE section starves,
- the tick cannot fire on the allocator hart (ticks=[0,0]),
- under oom01's exhaustion the slowpath never completes: the leader
  strands in_softirq forever, its SIGKILL cannot be delivered, the
  mm never frees, the allocator re-OOMs forever = THE WEDGE.

The ~100 s recoverable strands (pid 1100) are the same defect one
notch short of forever: the slowpath eventually completes.

## The fix (this branch, commit pending)

Linux discipline (wp_page_copy allocates the private copy BEFORE
taking the PTE lock): hoist alloc_user_phys_page() BEFORE the pte
guard with a Drop-guard (SpecPage) that frees the page on every
no-copy outcome — the section's re-checks already return Retry/
Resolved for those, so a wasted speculative page is just freed.
On pre-lock OOM the fault returns OutOfMemory with no lock held and
IRQs on. Applied to both the riscv64 and x86_64 twins.
