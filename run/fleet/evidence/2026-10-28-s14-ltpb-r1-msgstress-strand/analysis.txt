Adjudications
-------------
1. s13 slot-rewrite producer theory REJECTED at code level.
   IRQ-BRACKET-LEAK printed ZERO lines of any kind (when=slot/pre/in) during
   the 390-strand burst. Root cause of the null result: preempt bookings
   resolve through sched::current() which reads the ARCH tp REGISTER
   (sched.rs:5237), NOT cpu_state.current. The slot discriminators watch a
   path bookings never touch; a slot rewrite cannot split a bracket's
   +offset/-offset across tasks. The brackets stay as standing negatives.

2. PARKED-WILDWRITE pid 0x278 is a PROBE FALSE POSITIVE, not a wild write.
   The PARKED-LEAK line for the same task shows state=0x0 (TASK_RUNNING):
   a task preempted mid-switch-out holds the GRQ guard (count=1) while
   already slotless (the pick published `next`). The parkwalk's `running`
   classifier scans only cpu_state(c).current and predates R63's
   SWITCHING_OUT marker, so this legal window classifies as "parked".
   Under TCG thread=multi a host deschedule parks the vCPU exactly there
   for tens of ms, which is how the two consecutive walks sampled it.
   Probe fix (this session): running := slot-names-it OR
   task_is_mid_switch_out(task). This also stops the 4s PARKED-HEAL from
   zeroing a live guard mid-switch-out (which would re-open preemption
   inside the spinlock section and underflow the guard drop).

3. Family causal chain (all four faces, one engine):
   a parked/switching task RETAINS a leaked +1 (PARKED-LEAK face) -> when
   picked it runs unpreemptable (pc=1 incumbent face) -> every wake on the
   other CPU strands on the ~1s grid (WAKE-STRANDED 1001ms face) -> the
   pc=65537/65536 faces are the same leak with a stranded HARDIRQ bit.
   Missing piece: WHICH acquire site leaves the +1 (and the 0x10000).
