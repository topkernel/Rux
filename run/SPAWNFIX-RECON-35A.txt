REFERENCE (verbatim, re-checked this leg, not taken from either note)
/tmp/binder-5.10.c:4529, /tmp/binder-5.15.c:4200, /tmp/binder-6.1.c:4700
— the `done:` condition is WORD-IDENTICAL in all three:

    if (proc->requested_threads == 0 &&
        list_empty(&thread->proc->waiting_threads) &&
        proc->requested_threads_started < proc->max_threads &&
        (thread->looper & (BINDER_LOOPER_STATE_REGISTERED |
         BINDER_LOOPER_STATE_ENTERED))) { proc->requested_threads++;
        put_user(BR_SPAWN_LOOPER, buffer) }

Facts drawn from it:
1. done: is reached from every loop break, including after delivering
   a transaction — both commits agree here (the shared core fix), and
   both are CORRECT.
2. The cap is requested_threads_started (spawned-and-REGISTERED
   loopers), never the raw thread count. 635c4502 is right; 44ba45e2's
   threads.len() cap is a divergence (client-only BinderThread entries
   — FFRT workers, spawned children acting as clients — eat the
   max_threads budget they must not consume in Linux).
3. The returning thread must itself be a looper. 635c4502 has it;
   44ba45e2 does not (a client thread's reply-return could request
   spawns — Linux never does).
4. Rux-side soundness of the started counter (verified in our tree):
   requested_threads_started increments ONLY in BC_REGISTER_LOOPER
   (guarded by requested_threads>0, which it decrements) and is never
   decremented anywhere — exactly Linux's lifetime.

CANONICAL FORM (this branch: ab4ca01c, on top of f798ccd6)
Adopted 635c4502's predicate set verbatim into our binder.rs:
- non-child: requested_threads==0 && !ready && max_threads>0 &&
  requested_threads_started < max_threads &&
  (looper & (ENTERED|REGISTERED)) != 0
- child (sc164): child_n now counts only looper workers (children
  never REGISTER; client-only child threads must not eat the child
  budget — same principle).
`ready` = any thread waiting_for_proc_work = Linux's
list_empty(waiting_threads) inverted (same as before). The
`max_threads>0` guard both trees keep is redundant-but-harmless
(Linux relies on started<max being false at max==0).
The two branches' spawnfix cores are now SEMANTICALLY IDENTICAL;
merge either — the other's hunk drops out trivially. Their tree still
additionally carries poolcensus instruments; ours carries TXN-POOL.

STAGING-POSITION NUANCE (documented, no action)
Linux put_user's BR_SPAWN_LOOPER at buffer[0], OVERWRITING the
leading BR_NOOP staged at entry; Rux appends it after the (at most
one) sync transaction with a space check (staged.len()+4<=read_size,
sc79 discipline). Both produce valid return-command streams (NOOP and
SPAWN_LOOPER are no-payload commands; userspace processes them
sequentially) — external ABI intact.

FROM-WALK ADJUDICATION (predecessor's open question — CLOSED)
Question: is routing a nested sync call onto the SENDER's own todo
(the 5.10 from-walk) kernel-faithful, i.e. is the HDF mutual nesting
truly image-side?
Reference /tmp/binder-5.10.c:3018-3038 (binder_transaction):
sync call from a thread with a transaction stack walks tmp->from (via
from_parent); `from && from->proc == target_proc` -> target_thread =
from. binder_proc_transaction (2727) then enqueues on the TARGET
THREAD's todo (`binder_enqueue_thread_work_ilocked`) and wakes it
sync. Rux binder.rs ~6734 does exactly this (txn_stack rev walk,
from_proc == target, deliver to originator thread todo, wake) — the
sc333A2 decode ("619's nested call routed onto 469's own todo; 469
picked it, parked on a further nested call") is Linux behavior
verbatim.
Verdict: KERNEL ROUTING IS FAITHFUL. The residual wedges — our
sc333A2 accesstoken_ser-469 <-> foundation-619 cycle, OH-B's
composer_host <-> hdf_devmgr (txn11694/11696) and power_host <->
hdf_devmgr pairs — are image-side synchronous ABBA inversions; pool
growth cannot and should not break them. Image-side lane (OH-B) owns
them. No kernel change.
