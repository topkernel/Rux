### Round 2 — pointer instruments closed the gap

WRPUT/RDOD now print the buffer pointer; RXBHIT prints the block-cache
hit's pointer + first bytes; ZZERO-mat/ZZERO-hole print every
getblk_zero call site in the extent write path; caps raised, phys ring
2048. Boot xh4 (.ltp/diag/zzprobe4-xh4-verdict.log, C2 fails=5/5):

1. ZZERO-mat fires up to 79 times for ONE (ino=2261, logical=4,
   phys=114766): the unwritten->written conversion NEVER becomes
   visible to the next write's inode view — every writev of that chunk
   re-materializes the block.
2. Each re-materialization calls getblk_zero(phys); its HIT path
   fill(0)s the WHOLE 4 KiB block. zzprobe4/ftest04 interleave 2048-
   byte chunks from 5 forked writers into ONE file; every chunk
   boundary mid-block is a shared block, so each stale-view re-zero
   wipes the co-resident writer's span, and only the caller's own span
   is re-copied.
3. RXBHIT proves in-buffer data loss with pointer identity: the read
   hits the SAME buffer the WRPUTs wrote (blk=114765 b0=0000
   buf=0xffffffd6017d0000 immediately after repeated WRPUT pat=19 into
   that exact buffer) — no eviction, no fabrication, no dup in between.
4. The recycled-phys double mapping is visible: after the probe's
   recreate cycle logical=3 AND logical=4 both resolve to phys=114766.

ROOT CAUSE (two layers, fix belongs to the ext4 write-path owner):
- PRIMARY: get_data_block keeps returning 0 for blocks a previous
  write already materialized — the unwritten->written conversion (and
  write_inode extent updates generally) does not reach the state the
  next write's block resolution serves. NOT an SMP race (EXT4_BIG_LOCK
  serializes writes; the 79x repeat is the SAME pid serially) and NOT
  an inode-table staleness (read_inode and write_inode both go through
  bio::bread of the same inode-table block — cache-coherent; verified
  by code read this leg). The remaining candidate vectors, in scan
  order for the next leg: (a) the conversion lands in the write-local
  inode root but the NEXT write's resolution path walks a different
  extent view (e.g. external leaf written by write_node while the
  reader's root walk disagrees); (b) the probe's ftruncate rewrites
  extents as unwritten between iterations; (c) the recycled-phys
  double allocation (guest bitmap state after the file recreate)
  feeding Ok(Some(phys)) mats for the OLD instance's extent. One more
  print at get_data_block's unwritten verdict + ftruncate's extent
  rewrite closes it.
- AMPLIFIER: getblk_zero's HIT path whole-block fill(0) turns each
  stale "fresh block" verdict into destruction of live co-resident
  data. (That zero-on-hit was itself the r-era ftest05 fix for stale
  previous-life splices — bio.rs alone cannot distinguish a genuinely
  freed block from a still-mapped one; the extent truth must decide.)

Fix direction: make the unwritten->written conversion visible to the
next write's block resolution (write-through the inode extent state
under the journal handle, or consult the authoritative cached extent
view in the unwritten/hole decision). probe6s (below) is the
single-writer minimization for validating the fix.

{sa_handler +0, sa_flags +8, sa_mask +16} — NO sa_restorer. Evidence:
- Reference UAPI include/uapi/asm-generic/signal.h: the restorer
  member exists only `#ifdef SA_RESTORER`; riscv has no own
  uapi/asm/signal.h (404 on the canonical path) and nothing under
  arch/riscv defines SA_RESTORER.
- musl 1.2.5 (in-repo toolchain): arch/riscv64/bits/signal.h does
  not define SA_RESTORER -> the generic src/internal/ksigaction.h
  layout {handler, flags, mask} with the mask at +16 (sigsetsize 8).

  recorded in signal.rs since the r8-era fix).
